# 임팩트 버스트 크기 버그 + 보스 타겟팅 누락 버그 + 팀파니 홀드 밀도 - 검증 가이드

이 문서는 **Unity MCP가 연결된 별도 Claude Code 세션**에서 이번 작업을 실측 검증할 때 참고하는
절차서입니다. 사용자의 실제 플레이 테스트로 발견된 버그 2건을 수정했습니다. 아직 커밋하지 않은
상태입니다.

검증이 끝나면 이 파일 하단에 결과를 추가로 append해주세요.

## 0. 무엇을 고쳤나

### 0-1. 임팩트 버스트가 실제 타격범위보다 훨씬 크게 보이던 버그

`AreaImpactEffect`(글록켄슈필/팀파니가 쓰는 예고→착탄 이펙트)가 9프레임 스파크 애니메이션을 붙인 직후
(`impact_burst_sprite_animation_test_guide.md`), 실측 결과 이펙트가 실제 타격범위보다 훨씬 크게(눈이
아플 정도로) 보인다는 리포트가 있었습니다.

원인은 **이중 확대**였습니다:
- 예전 다이아몬드는 캔버스(20px) 대비 도형이 아주 작아(반지름 9px), `transform.localScale = radius*1.6`을
  곱해도 화면상 지름은 `radius`의 약 29%에 불과했습니다(원래도 "정확한 반경 표시"가 아니라 작은 착탄
  팝 마커였음).
- 새 스파크 프레임은 임포트 시 알파 기준으로 트림되어, 특히 최대로 만개한 프레임(spark5)은 캔버스를
  거의 꽉 채웁니다. 여기에 그대로 `radius*1.6`을 곱하니 실제 지름이 `radius`의 7배 이상으로 뻥튀기됐고,
  프레임마다 트림된 크기가 제각각이라(spark1은 작고 spark5는 큼) 프레임이 바뀔 때마다 크기도 들쭉날쭉
  했습니다.

`InstrumentOrbit`의 "최대 치수 정규화"와 동일한 방식으로 재설계했습니다:
- `peakDiameter = radius * 2f` (착탄 순간=가장 만개한 프레임의 화면상 지름이 정확히 실제 판정 반경의
  지름과 같아지도록).
- 매 프레임 `frame.bounds`의 실제 콘텐츠 최대 치수로 나눠서 스케일을 계산 - 어떤 프레임이 보이든
  화면상 크기는 항상 의도한 값과 일치합니다.
- 생애주기(0=예고 시작 → 0.5=착탄 → 1=플래시 끝) 전체에 걸쳐 삼각형 곡선(양 끝 15% 크기 → 중앙 100%)을
  적용해 "작게 시작 → 실제 반경 크기로 만개 → 다시 작아지며 소멸"이 되도록 했습니다.
- 사용처(글록켄슈필/팀파니)나 폴백(에셋 없을 때 다이아몬드) 모두 같은 로직을 공유합니다.

### 0-2. 보스 단독 페이즈에서 일부 악기가 보스를 인식 못 하던 버그(+ 확장 조사)

사용자가 "최종보스만 남았을 때 글록켄슈필/팀파니가 보스를 인식 못 하고 플레이어 위치에서 공격한다"고
리포트했습니다. 다른 악기도 점검해달라는 요청에 따라 `CombatTargetingUtility`와 각 악기 이펙트 전체를
훑었고, 두 가지 별개의 문제를 찾았습니다.

**(A) 타겟 위치를 못 찾는 문제(리포트된 증상)**: `CombatTargetingUtility.GetNearestEnemy`/
`GetHighestHpEnemy`는 `EnemySpawner.ActiveEnemies`(`EnemyMonster`)만 보고 `BossMonster`는 전혀 고려하지
않습니다. 잡몹이 0마리이고 보스만 있으면 항상 `null`을 반환해, 호출부가 `origin`(플레이어 위치) 또는
고정 방향(`Vector3.up`)으로 폴백합니다. 이 문제가 있던 5곳:

| 악기 | 증상 |
|---|---|
| 벨 (`BellStarburstEffect`) | 8방향 성광의 중심이 플레이어 위치로 감 |
| 피아노 (`PianoBeamEffect`) | 레이저가 무조건 위쪽(`Vector3.up`)으로 발사됨 |
| 첼로 (`CelloGravityFieldEffect`) | 중력장이 플레이어 발밑에 생성됨 |
| 팀파니 (`TimpaniBombardmentEffect`) | 캐논/융단폭격이 플레이어 위치를 계속 폭격 |
| 글록켄슈필 (`GlockenspielStarfallEffect`) | 별빛 낙하 지점이 플레이어 위치가 됨 |

`CombatTargetingUtility`에 `GetNearestTargetPosition`/`GetHighestHpTargetPosition` 헬퍼를 추가해
(잡몹이 있으면 기존과 동일하게 잡몹 우선, 잡몹이 0마리일 때만 보스를 폴백으로 사용) 5곳 모두 교체했습니다.

**(B) 피해 자체가 아예 안 들어가는 문제(조사 중 추가로 발견)**: 위와는 별개로, 지속 틱 피해를 주는
3개 악기의 홀드 이펙트가 데미지 루프 자체에서 `BossMonster`를 아예 체크하지 않아서, **보스가 사거리
안에 있어도 데미지가 0**이었습니다(잡몹 유무와 무관하게 항상 발생하는 문제 - 보스전 내내 해당).

| 악기 | 영향받은 부분 | 영향 없는 부분 |
|---|---|---|
| 프렌치 호른 (`FrenchHornConeEffect`) | 부채꼴 지속 충격파 틱 데미지 | - |
| 첼로 (`CelloGravityFieldEffect`) | 중력장 지속 틱 데미지 | - |
| 바이올린 (`ViolinOrbitEffect`) | 회전 칼날 지속 틱 데미지 | 릴리즈 참격(빔이라 원래도 보스 적중 정상) |

세 곳 모두 다른 곳(`AreaImpactEffect`, `TimpaniBombardmentEffect`, `DrumBeatBangEffect` 등)과 동일한
관례로, 보스에게는 넉백/디버프/감속 같은 EnemyMonster 전용 부가효과 없이 데미지만 적용하도록 추가했습니다.

**점검 결과 이미 정상이던 것**: 드럼/피아노/벨/마림바/글록켄슈필(빔 또는 `AreaImpactEffect`/
`PiercingBeamProjectile` 경유)은 원래부터 보스 데미지 처리가 있었습니다. 플루트는 원래 무피해 CC
전용이라(기획 의도) 보스가 안 끌려가는 것도 버그가 아니라 "보스는 CC 면역"에 해당하는 자연스러운
결과로 판단해 손대지 않았습니다 - 만약 플루트가 보스도 밀어내야 한다고 생각하시면 알려주세요.

### 0-3. 팀파니 고레벨 홀드가 쉴 틈 없이 이어지던 문제

사용자가 "팀파니가 레벨이 오를수록 키다운이 끝나자마자 바로 다음 키다운이 온다"고 리포트했습니다.
조사 결과 `RhythmManager.ProcessSequencerStep`의 홀드 겹침 방지 로직(같은 레인에 홀드가 진행 중이면
새 온셋 무시 - 정상적인 방어 로직) 자체는 문제가 없었지만, 팀파니의 홀드 길이(`holdLengthSteps`)가
기존 16스텝으로 32스텝 사이클의 정확히 절반이었고 Lv1~5 패턴 전부에 스텝0/16 온셋이 공통으로 있어서,
**레벨과 무관하게 항상 정확히 2회/사이클만 실제 홀드가 발동**하고 있었습니다(Lv3~5가 패턴에 추가한
"격렬해지는" 온셋들은 전부 겹쳐서 조용히 스킵됨 - 애초에 레벨업으로 밀도가 올라가는 효과가 없었음).
사용자 결정(2026-08-08, "홀드 길이를 줄여서 실제 쉬는 구간 확보")에 따라 `holdLengthSteps[Timpani]`를
16→10으로 줄였습니다: 32스텝 사이클마다 "홀드 10칸 + 휴식 6칸"이 2회 반복되는 구조가 됩니다(모든
레벨 동일 - 레벨별 강도 차이는 `TimpaniBombardmentEffect`의 범위/빈도/기절/지진지대 수치가 이미
담당하므로 패턴 자체는 손대지 않았습니다). `InstrumentPatternDatabase.cs`의 Timpani 패턴 주석("N
hits")도 실제 발동 횟수(항상 2회)에 맞게 정정했습니다.

## 1. 사전 준비

1. `refresh_unity(mode=force, compile=request)` → `read_console`로 컴파일 에러 확인.
2. 보스(엘리트 또는 최종보스) 단독 페이즈를 재현해야 확인 가능합니다 - 테스트 씬에서 잡몹을 모두
   제거하고 `BossMonster` 인스턴스만 남긴 상태를 만들거나, 리플렉션으로 각 이펙트의 타겟팅 결과를
   직접 확인하는 방식도 가능합니다.

      적용 시도하지 않고 에러 없이 넘어가는지

- [ ] **회귀**: 글록켄슈필 2차 유도 파편(Lv5)의 "1차 타겟 제외" 로직이 여전히 정상 동작하는지

### 팀파니 홀드 밀도
- [ ] Lv1~5 전부에서, 한 홀드가 끝난 뒤 다음 홀드 온셋까지 실제로 쉬는 구간(약 6스텝)이 생기는지
- [ ] 홀드 길이가 실제로 10스텝(`stepDuration * 10`초)인지 (`RhythmNote.HoldDurationSeconds` 확인)
- [ ] 레벨이 올라가도 홀드 자체의 발동 빈도/길이는 거의 동일하고, 대신 개별 홀드 안의 폭격 빈도/범위/

- [ ] **회귀**: 다른 홀드 악기(바이올린/프렌치호른/첼로)의 홀드 길이는 이번 변경과 무관하게 그대로인지

## 4. 검증 결과

**검증 일시**: 2026-08-08, Unity MCP 연결 세션(`My project@c018c67b9a01a4e5`, Unity 6000.5.5f1)

**1절 사전 준비**: `refresh_unity(force, compile=request)` → 컴파일 에러/경고 0건. 실시간 Update 루프가
에디터 창 포커스 손실로 정체되는 현상(이전 세션에서도 관찰됨)이 있어, 리플렉션 기반 결정론적 호출 +
`BossMonster`/`EnemyMonster`를 코드로 직접 스폰하는 방식으로 "잡몹 0마리 + 보스만" 상황을 재현했다
(1절이 제안한 두 방법 중 후자).

### 크기 버그

- [x] **스파크 지름 = radius×2 일치**: `AreaImpactEffect.ApplyFrame()`을 리플렉션으로 직접 호출해
      `radius=1.5`일 때 progress 0/0.1/0.25/0.4/0.5/0.6/0.75/0.9/1.0 전 구간에서 "화면상 지름
      (localScale × frame.bounds 최대 치수)"을 실측 → 9개 지점 전부 기대값(삼각형 곡선:
      0.45→0.96→1.725→2.49→3.0→2.49→1.725→0.96→0.45)과 소수점 4자리까지 정확히 일치(`match=True`
      전부). 착탄 순간(progress=0.5, spark5)에서 정확히 `radius*2=3.0`으로 확인.
- [x] **프레임이 바뀌어도 크기 안정**: 위 실측에서 각 프레임의 원본 콘텐츠 크기(raw maxDim)는
      spark1(0.65)~spark5(4.72)로 7배 이상 들쭉날쭉했지만, 정규화 후 화면상 지름은 오직 progress
      값(=생애주기상 위치)에만 좌우되고 프레임 원본 크기와 무관하게 항상 의도한 곡선값과 일치함을
      확인 - "이중 확대" 버그가 실제로 고쳐졌음을 수치로 증명.
- [x] **시각 확인**: `radius=1.0`에 실제 판정 반경을 정확히 표시하는 빨간 기준 링(`CreateUnitRing`,
      scale=radius)을 겹쳐 그리고 착탄 순간(progress=0.5) 스크린샷 촬영 → 스파크 별 모양의 뾰족한
      끝이 기준 링 경계에 정확히 맞닿는 것을 육안 확인(이전 버그였다면 화면을 뒤덮을 정도로 컸을 것).
- [x] **크레센도(범위 배율)로 radius가 커지면 비례 확대**: `radius=0.7/1.5/3.0` 세 값에 대해
      착탄 순간(progress=0.5) 지름을 각각 실측 → 1.4/3.0/6.0으로 정확히 `radius*2`에 선형 비례함을 확인.
- [x] **폴백 상황에서도 정상 크기**: 이전 애니메이션 검증 때와 동일한 방식(정적 필드 리플렉션으로
      `burstFrames=null` 강제)으로 "에셋 없음" 상황을 재현 → 다이아몬드 스프라이트가 그대로 쓰이면서도
      같은 정규화 공식이 적용되어 착탄 순간 지름이 정확히 `radius*2`(1.5→3.0)로 나옴을 확인. 테스트 후
      정적 필드는 원래 캐시된 9프레임으로 복원.

### 보스 타겟팅

- [x] **잡몹 0 + 보스만 있을 때 5개 악기가 보스를 정확히 겨냥**: 플레이어를 원점에, 보스를 (6,4,0)에
      배치하고 `CombatTargetingUtility.GetNearestTargetPosition`/`GetHighestHpTargetPosition`을 벨/
      첼로/팀파니/글록켄슈필이 쓰는 그대로 호출 → 전부 보스 좌표(6,4,0)와 정확히 일치. 피아노는 방향
      벡터(`targetPos - origin`)를 계산해 보스를 향한 방향(0.83, 0.55)과 정확히 일치함을 확인. 추가로

- [x] **레벨과 무관하게 정상상태 2회/사이클 + 6스텝 휴식**: `RhythmManager.ProcessSequencerStep`의
      겹침 방지 로직을 실제 `GetPattern`/`GetHoldLengthSteps` 데이터로 재현해 32스텝 사이클 4개
      연속(128스텝) 시뮬레이션. Lv1/2/4/5는 매 사이클 정확히 2회(Step 0, 16 반복, 휴식 6스텝)로
