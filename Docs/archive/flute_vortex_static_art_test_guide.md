# 플루트 소용돌이 정지 이미지 연동 - 검증 가이드

이 문서는 **Unity MCP가 연결된 별도 Claude Code 세션**에서 이번 작업을 실측 검증할 때 참고하는
절차서입니다. 아직 커밋하지 않은 상태입니다. 사용자가 다른 이펙트들과 묶어서 한 번에 테스트하기로
해서, 아래 항목들은 그 배치 테스트에 포함해주시면 됩니다.

검증이 끝나면 이 파일 하단(4절)에 결과를 추가로 append해주세요.

## 0. 무엇을 고쳤나

`FluteVortexEffect`에 손그림 정지 이미지 1장(`Assets/Resources/Sprites/Effects/Vortex/Vortex.png` -
동심원 형태 초록 소용돌이)을 붙였습니다. 영상 생성 토큰이 소진되어 이번 이펙트는 영상/프레임 추출
없이 정지 이미지 한 장만 쓰기로 사용자가 결정.

- **정지 이미지 + 펄스로 대체**: 동심원 패턴은 회전시켜도 완전 대칭이라 시각적으로 변화가 없습니다.
  그래서 다른 이펙트들처럼 프레임을 순환하는 대신, `Update()`에서 `Mathf.Sin` 기반으로 아트 전용 자식
  오브젝트(`FluteFieldArt`)의 스케일을 ±6% 범위로 "숨쉬듯" 주기적으로 펄스시킵니다(`PulseSpeed=2.2`
  라디안/초). 판정 반경(`radius`)이나 흡입력(`pullStrength`)에는 전혀 영향 없는 순수 시각 효과입니다.
- **이중 확대 버그 사전 방지**: 첼로/빔과 동일한 패턴 - 기존엔 루트 `transform.localScale = radius*0.9`를
  절차적 원의 시각 크기와 범위 링 보정(`1/0.9`) 양쪽에 재사용했는데, 손그림 아트는 콘텐츠 크기가
  달라 그대로 두면 이중 확대가 났을 것입니다. 아트를 `FluteFieldArt`라는 별도 자식 오브젝트로 분리해
  `sprite.bounds` 기준으로 독립 계산(`ApplyArt`)하고, 루트는 identity로 두어 범위 링도 `radius`를
  직접 곱하는 방식으로 단순화했습니다.
- **색상**: 아트 자체가 이미 초록 톤으로 그려져 있어 색상 틴트는 걸지 않고, 알파만 0.4로 곱해 기존과
  동일하게 반투명(장판 아래 적이 비쳐 보임)을 유지합니다.
- 스프라이트 로딩 실패 시(에셋 미존재 등) 기존과 동일한 절차적 원(`CreateFilledCircle(28,13f,녹색)`)으로
  폴백하며, 폴백 시 크기도 기존 공식과 수학적으로 동일한 결과가 나오도록 정규화했습니다.

## 1. 사전 준비

1. `Assets/Resources/Sprites/Effects/Vortex/Vortex.png`에 아직 `.meta`가 없다면
   `refresh_unity(mode=force, compile=request)`로 최초 임포트.
2. Texture Type = **Sprite (2D and UI)** 확인.
3. `refresh_unity(force, compile=request)`로 재적용 후 컴파일 에러/경고 0건 확인.

## 2. 검증 항목

- [ ] 플루트 홀드 릴리즈 시 절차적 원 대신 새 소용돌이 아트가 보이는지
- [ ] 아트가 ±6% 범위로 부드럽게 숨쉬듯 펄스하는지(형태는 그대로, 크기만 미세하게 변화)
- [ ] **크기 검증**: `ApplyArt()`를 리플렉션으로 호출해 `fieldArtTransform.localScale × sprite.bounds.size`가
      기존 절차적 원 기준(`radius*0.9*0.28`)과 동일한 지름으로 나오는지, Lv3(흡입범위+50%)처럼
      `radius`가 커질 때 그 비율 그대로 커지는지
- [ ] 범위 링(`FluteRangeRing`)이 실제 흡입 반경(`radius`)과 정확히 일치하는지(루트 스케일 단순화
      이후에도 회귀 없는지)
- [ ] 폴백 상황(에셋 없음 가정)에서 기존 절차적 원과 수학적으로 동일한 크기가 나오는지(회귀)
- [ ] **회귀**: 적을 중앙으로 끌어당기는 로직(`pullStrength`)이 이번 변경과 무관하게 정상 동작하는지
- [ ] **회귀**: Lv4 동시 2개 유지(오래된 소용돌이 강제 정리)가 정상 동작하는지
- [ ] **회귀**: Lv5 소멸 시 바람 파편(외곽 넉백)이 정상 동작하는지

## 4. 검증 결과

**검증 일시**: 2026-08-08, Unity MCP 연결 세션(`My project@c018c67b9a01a4e5`, Unity 6000.5.5f1) - 첼로/
프렌치호른/잔류장판/바이올린 칼날과 함께 배치 테스트로 진행.

**1절 사전 준비**: `refresh_unity(force, compile=request)`로 최초 임포트, `.meta` 자동 생성, 컴파일
에러/경고 0건.

- [x] **정지 이미지 표시**: `FluteVortexEffect.Initialize()`를 Play Mode에서 직접 호출해 확인.
      `Resources.LoadAll("Sprites/Effects/Vortex")`가 `Vortex_0` 1장을 정확히 로드함.
- [x] **±6% 펄스**: `Update()`를 15회 반복 호출(dt≈0.02)해 `fieldArtTransform.localScale`을 매 틱
      기록한 결과, `baseArtScale × (1 + Sin(elapsed×2.2)×0.06)` 공식과 소수점 6자리까지 정확히 일치.
      판정 반경에는 영향 없음(별도 `radius` 필드로 분리되어 펄스와 무관하게 유지됨을 코드로 확인).
- [x] **크기 검증**: `ApplyArt()`를 실제 아트(`Vortex_0`, contentMaxDim≈19.28)와 폴백 원
      (`CreateFilledCircle(28,13f,...)`, contentMaxDim=0.28) 양쪽에 호출한 결과 `visDiameter`가 둘 다
      **0.504000**로 완전히 동일(=`radius(2.0)×0.9×0.28`). 이중 확대 없음.
- [x] **범위 링 정확성**: Lv3(흡입범위 +50%) 테스트에서 `radius`가 2.0→3.0으로 정확히 커지고
      `FluteRangeRing` 스케일도 정확히 3.0으로 일치.
- [x] **회귀 - 끌어당김(`pullStrength`)**: 적을 반경 안에 배치 후 `Update()` 1틱 호출 →
      `pullStrength(2.5)×dt(0.02)=0.05` 만큼 정확히 중심으로 이동, 피해는 없음(순수 CC 설계 유지)을
      확인.
- [x] **회귀 - Lv4 동시 2개 유지**: Lv4 소용돌이 3개를 순서대로 생성 → `activeVortices` 정적 리스트가
      정확히 최신 2개만 유지(`Count=2`)하고 가장 오래된 것을 트래킹에서 제거함을 확인(실제
      `GameObject` 파괴는 `Destroy()`가 프레임 종료 시점까지 지연되는 이 환경 특성상 즉시 보이지
      않았으나, 리스트 캡 로직 자체는 정확 - 하단 참고).
- [x] **회귀 - Lv5 바람 파편**: `ExplodeWindShard()`를 직접 호출 → 반경 내 적이 `0.8` 만큼 바깥으로
      정확히 밀려나고 피해는 0(변경 없음, 기존 무피해 CC 설계 유지)임을 확인.

**부가 관찰**: 에디터 창 포커스 상실로 인한 `Time.time` 정체/`Destroy()` 지연 반영 환경 특성은 다른
문서들과 동일하게 재현됨 - 리플렉션 기반 결정론적 호출로 우회.

**결론**: 정지 이미지 + 펄스 방식이 설계 의도대로 정상 동작. 크기 정규화/범위 링/끌어당김/Lv4 캡/Lv5
바람 파편 전부 회귀 없음. 코드 변경 불필요, 추가 조치 없음.
