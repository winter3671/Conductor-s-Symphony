# 배경 스크롤 - 셰이더 방식 폐기 후 격자 재배치 방식으로 재작성 - 검증 가이드

이 문서는 **Unity MCP가 연결된 별도 Claude Code 세션**에서 이번 작업을 실측 검증할 때 참고하는
절차서입니다. 아직 커밋하지 않은 상태입니다.

검증이 끝나면 이 파일 하단(4절)에 결과를 추가로 append하고, `archive/`로 옮겨주세요.

## 0. 무엇을 고쳤나 - 그리고 이전 PASS 판정이 왜 틀렸는지

`archive/background_worldlock_scroll_test_guide.md`에서 "PASS"로 기록됐던 배경 스크롤 수정이
**사용자의 실제 수동 플레이에서 재현되지 않음**(배경이 여전히 화면에 고정되어 캐릭터가 움직여도
무늬가 안 바뀜)이 다시 보고됐습니다.

- **이전 PASS 판정이 틀렸던 이유**: 이전 검증(4-2절)은 `material.mainTextureOffset` 값을
  리플렉션으로 읽어서 "코드가 계산한 값이 공식과 일치하는지"만 확인했고, 4-6절의 "실제 아트로
  이동감 확인"도 스크린샷 두 장을 비교해 육안으로 "달라 보인다"고 판단한 것이었습니다. 그런데
  **`Sprites-Default`를 비롯한 대부분의 스프라이트 셰이더는 `_MainTex_ST`(Tiling/Offset)를 셰이더
  코드에서 아예 읽지 않습니다** - 스프라이트는 원래 아틀라스 패킹으로 텍스처 좌표를 정점에 미리
  구워두는 방식이라, 머티리얼의 Tiling/Offset 프로퍼티로 스크롤시키는 걸 애초에 지원하지 않는
  구조입니다. 즉 `materialInstance.mainTextureOffset = uvOffset;`은 그 프로퍼티 값 자체는 정상
  설정되지만(그래서 리플렉션으로 값만 읽으면 공식과 일치해 보임), 실제 렌더링에는 전혀 반영되지
  않았던 것입니다. 리플렉션 기반 수치 검증의 함정 - "값이 올바르게 설정됐다"와 "그 값이 실제로
  화면에 영향을 준다"는 다른 문제인데, 이번엔 후자를 검증하지 못했습니다.
- **수정(전면 재작성)**: `Assets/Scripts/Environment/BackgroundTiler.cs`에서 셰이더/머티리얼에
  의존하는 방식을 완전히 버리고, **실제 타일 스프라이트 여러 장을 격자(그리드)로 배치해서 카메라를
  따라 재배치하는 고전적인 방식**으로 재작성했습니다.
  - `Awake()`에서 화면(카메라 `orthographicSize`/`aspect`)을 덮는 데 필요한 최소 타일 수 + 여유분
    (`gridPaddingTiles`, 기본 1)을 계산해 `gridSize x gridSize`(홀수, 최소 3x3) 개의 자식
    `SpriteRenderer` 오브젝트를 미리 생성.
  - `LateUpdate()`에서 카메라의 월드 좌표를 타일 크기로 나눠 "카메라가 지금 어느 격자 칸에 있는지"
    계산하고, 매 프레임 모든 타일을 그 칸을 중심으로 한 정확한 월드 격자 좌표(`격자칸 × 타일크기`)에
    재배치. 텍스처/머티리얼/셰이더는 전혀 안 건드리고 순수 `Transform.position` 계산만 사용하므로
    셰이더가 뭘 지원하든 확실하게 동작함.
  - 이 오브젝트 자체가 갖고 있던 기존 `SpriteRenderer`(1차 시도의 Tiled 덮개)는 비활성화만 하고
    스프라이트 출처로만 재사용(`selfRenderer.sprite`) - 이중 렌더링 방지.
- 판정/스폰/밸런스 등 다른 로직은 전혀 건드리지 않았다.

## 1. 사전 준비

1. `refresh_unity(force, compile=request)`로 재컴파일 - 컴파일 에러/경고 0건 확인.
2. 씬의 기존 `Background` 오브젝트(`Assets/Prefabs/Environment/Background.prefab` 인스턴스)를
   그대로 써도 됨 - 스크립트가 알아서 자기 SpriteRenderer를 끄고 자식 타일들을 만든다. 프리팹
   자체를 다시 만들 필요는 없어 보이지만, 만약 프리팹에 저장된 `tileSprite` 필드가 비어있다면
   기존 SpriteRenderer의 sprite(ParquetFloor)를 자동으로 가져오는지 확인 필요.

## 2. 검증 항목

- [ ] 컴파일 에러/경고 0건
- [ ] **타일 격자 생성 확인**: Play 모드 진입 시 `Background` 오브젝트 하위에 `Tile_x_y` 이름의
      자식 오브젝트들이 실제로 생성되는지(리플렉션으로 `tiles` 배열 크기, 또는 `transform.childCount`
      확인). 화면 크기 대비 격자가 충분히 큰지(가장자리에 빈틈 안 보이는 정도) 확인.
- [ ] **원본 SpriteRenderer 비활성화 확인**: 루트 오브젝트의 기존 `SpriteRenderer.enabled`가
      `false`인지 확인(이중 렌더링/겹침 없어야 함).
- [ ] **이동감 - 핵심, 반드시 실제 화면 스크린샷으로 확인**: 플레이어를 한 방향으로 이동시키며 여러
      시점에 스크린샷을 찍어서, 화면 안에서 마룻바닥 무늬(헤링본 이음선)의 화면상 픽셀 위치가 실제로
      달라지는지 확인. **이전처럼 `mainTextureOffset`류 프로퍼티 값만 읽어서 판단하지 말고, 반드시
      스크린샷 상에서 특정 이음선/특징점의 화면 좌표가 이동 전후로 달라지는지 직접 대조할 것** -
      이전 세션이 이 부분을 제대로 못 잡아서 재작성까지 왔음을 감안해 이번엔 더 엄격하게 확인 필요.
- [ ] **타일 재배치(래핑) 확인**: 플레이어를 타일 크기(약 17유닛) 이상 이동시켰을 때, 뒤로 멀어진
      타일이 반대편(진행 방향 앞쪽)으로 재배치되어 화면이 계속 덮이는지 확인. 이 순간 눈에 띄는
      팝인/깜빡임/빈틈이 없는지 확인(타일이 카메라 시야 밖에서 재배치되므로 원래는 안 보여야 함).
- [ ] **왕복 이동 시 일관성**: 특정 방향으로 이동했다가 반대로 되돌아왔을 때, 화면에 보이는 무늬가
      원래 봤던 자리로 정확히 돌아오는지 확인.
- [ ] **성능**: 격자 크기(`gridSize x gridSize`, 예상 5x5~7x7 정도)만큼 `SpriteRenderer`가 새로
      생기는데, 전부 같은 스프라이트/머티리얼을 공유해서 배치(batching)가 잘 되는지, 프레임레이트에
      눈에 띄는 영향이 없는지 확인.
- [ ] **화면 비율/해상도 변경 대응**: `orthographicSize`나 화면 비율을 바꿔도(에디터 Game 뷰 크기
      조절 등) 격자가 여전히 화면을 다 덮는지 확인(단, 이번 구현은 `Awake()` 시점에 격자 크기를
      한 번만 계산하므로, 런타임 중 화면 크기가 바뀌면 격자가 부족해질 수 있음 - 문제 있으면 보고
      바람. 필요시 `BuildGrid()`를 화면 크기 변경 감지 후 재호출하도록 개선 필요).
- [ ] **기존 게임플레이 회귀 없음**: 몬스터 스폰/판정/UI 등 배경과 무관한 기존 동작이 그대로인지
      확인.

## 4. 검증 결과

**검증 환경**: Unity 6000.5.5f1, `Gameplay.unity` 씬. `Assets/Scripts/Environment/BackgroundTiler.cs`는
이미 커밋된 상태(작업 트리에 diff 없음, `git status` 확인)로, 문서 0절에 기술된 재작성 버전이 실제
파일 내용과 일치함을 먼저 확인한 뒤 진행. 참고: 에디터 창이 언포커스 상태라 Play 모드 진입 후에도
`Time`/프레임이 실시간으로 자동 진행되지 않아(도구 호출 사이에 `Time.frameCount`가 거의 멈춰있음),
이동 검증은 플레이어/카메라 좌표를 직접 설정한 뒤 `CameraController.LateUpdate()`와
`BackgroundTiler.LateUpdate()`를 리플렉션으로 **실제 프로덕션 메서드 그대로** 수동 구동해 화면을
렌더링하는 방식으로 진행(이전 세션에서 실패했던 "값만 읽고 실제 렌더링 결과는 확인 안 함" 함정을
피하기 위해, 매 단계마다 반드시 스크린샷으로 화면에 그려진 결과까지 대조함).

- [x] **컴파일 에러/경고 0건**: `refresh_unity(force, compile=request)` 이후 `read_console` 0건.
- [x] **타일 격자 생성 확인**: Play 모드 진입 후 `Background` 오브젝트의 `transform.childCount=25`,
      리플렉션으로 읽은 `tiles` 배열도 `5x5`(=25)로 일치. `gridSize=5`, `tileWorldSize=17.1`도
      `BuildGrid()` 공식(화면 필요 타일수 4x3 + 패딩 → 홀수 보정)대로 정확히 계산됨을 역산 검증.
      `Tile_0_0`~`Tile_0_4` 등 자식 이름 패턴도 코드와 일치.
- [x] **원본 SpriteRenderer 비활성화 확인**: 루트 오브젝트의 기존 `SpriteRenderer.enabled == false`
      확인.
- [x] **이동감 - 스크린샷 실측**: 플레이어를 (0,0,0)→(5,0,0)으로 이동 후 카메라/배경 스크립트를
      실제 코드로 재구동해 스크린샷 비교. 월드 고정 오브젝트(근처 몬스터)의 화면상 픽셀 이동량이
      약 220px로, 이론값(5 world unit × 화면폭/시야폭 ≈ 43.2px/unit ≈ 216px)과 거의 정확히 일치.
      배경 무늬(헤링본 이음선) 자체도 두 스크린샷에서 육안으로 명백히 다른 위치에 그려짐 - 이전
      세션이 놓쳤던 "실제로 화면에 반영되는지"를 스크린샷 픽셀 단위로 직접 확인함.
- [x] **타일 재배치(래핑) 확인**: 플레이어를 타일 크기(17.1)를 넘는 25유닛까지 이동 → 격자 중심
      칸이 `round(25/17.1)=1`로 재계산되어 타일 좌표 범위가 `[-17.1, 51.3]`으로 이동함을 확인(코드
      공식과 정확히 일치). 이 상태에서 카메라가 필요로 하는 시야 범위(X:[16.1,33.9], Y:[-5,5])가
      타일 커버리지(X:[-25.65,59.85], Y:[-42.75,42.75]) 안에 완전히 포함됨을 수치로 확인, 스크린샷
      에서도 빈틈/이음매 없이 화면 전체가 정상적으로 덮여 있음을 확인.
- [x] **왕복 이동 시 일관성**: (25,0,0)에서 다시 (0,0,0)으로 되돌린 뒤 재구동 → 타일 5개 좌표가
      최초 baseline과 소수점까지 완전히 동일하게 복원됨을 확인. 스크린샷도 최초 baseline과 무늬
      배치가 픽셀 단위로 동일해 보임(왕복 후 어긋남 없음).
- [~] **성능(배칭)**: 프로파일러 카운터(`Batches Count`/`Draw Calls Count`)가 이번 자동화 세션
      환경(에디터 언포커스, 스크린샷은 일반 플레이어 루프를 거치지 않는 직접 카메라 렌더링)에서는
      `_valid:false`로 나와 실측 수치를 얻지 못함 - **한계로 남겨둠, 실제 사용자 수동 플레이 중
      Profiler 창에서 직접 확인 권장**. 다만 25개 타일 전부 동일 스프라이트(`ParquetFloor`)/동일
      머티리얼/동일 sortingOrder(-100)를 공유하므로 Unity 동적 배칭 조건을 만족해 드로우콜이 소수로
      묶일 것으로 코드상 합리적으로 기대됨(경험적 확인은 아님, 명시적으로 구분).
- [x] **화면 비율/해상도 변경 대응**: 문서에 이미 예고된 한계 그대로 재현됨 - `orthographicSize`를
      5→30으로(사전 계산된 격자 커버리지 ±42.75보다 필요 시야 ±53.33이 더 큰 상황) 늘린 뒤
      재구동하니 화면 좌우 가장자리에 무늬 없는 단색 띠(격자 커버리지를 벗어난 빈 영역)가 스크린샷
      상에서 명확히 확인됨. `BuildGrid()`가 `Awake()` 시점 1회만 계산하기 때문에 발생하는 것으로,
      코드 주석에도 명시된 알려진 한계와 정확히 일치. 필요 시 화면 크기 변경 감지 후 `BuildGrid()`
      재호출 개선이 필요함(이번 검증 범위에서는 수정하지 않음).
- [x] **기존 게임플레이 회귀 없음**: `git diff --stat` 확인 결과 이번 스코프에서 `BackgroundTiler.cs`
      외 다른 스크립트(몬스터 스폰/판정/UI 등)는 변경 이력이 전혀 없음(코드 자체가 순수
      환경/렌더링 격리 - `Transform.position`만 다루고 다른 시스템을 참조하지 않음). Play 모드 진행
      중 콘솔에도 관련 에러/경고 없음(Unity AI Toolkit 계정 API 관련 무관한 경고 1건만 존재, 이번
      변경과 무관).

**결론**: 이전 세션의 PASS 오판(셰이더 트릭이 실제로는 렌더링에 반영 안 됨)의 원인이었던 "리플렉션
수치만 확인"의 함정을 피해, 이번엔 스크린샷 픽셀 단위 대조 + 실제 프로덕션 코드 직접 구동으로
재검증한 결과 이동감/래핑/왕복 일관성 모두 실제로 화면에 정상 반영됨을 확인. 유일하게 남은 이슈는
문서에 이미 예고됐던 "런타임 화면 크기 변경 시 격자 부족" 한계로, 이는 버그라기보다는 알려진
제약사항(현재 게임의 `orthographicSize`/화면 비율이 런타임에 바뀌지 않는다면 실무상 영향 없음)이라
커밋 가능한 상태로 판단됨. 성능(배칭) 수치만 이 자동화 환경의 한계로 실측하지 못해 수동 재확인을
권장.
