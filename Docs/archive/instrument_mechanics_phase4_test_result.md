# 10종 악기별 공격 메커니즘 - 4단계(밸런스 doc 정합화) 검증 결과

`instrument_mechanics_phase4_test_guide.md`에 정리된 절차에 따라 **Unity MCP(Unity 6000.5.5f1,
`My project` 인스턴스)**로 실측 검증을 진행한 결과입니다. 1~3단계에서 정립한 방법론
(`Time.timeScale=0` + 리플렉션으로 private 필드/메서드 직접 제어)을 기본으로 사용하되, 이번 라운드는
신규 상태이상 인프라(`EnemyMonster`)와 잔류 장판/유도 파편 등 `Time.deltaTime`을 메서드 내부에서 직접
읽는 신규 클래스가 여럿 추가되어 방법론을 한 단계 더 확장했습니다 (아래 "테스트 방법론" 참고).

**종합 결과: 10종 전체(드럼/피아노/바이올린/프렌치호른/첼로/팀파니/마림바/글록켄슈필/벨/플루트) 및
공용 상태이상 인프라(`EnemyMonster`) 전부 PASS. 치명적 버그 없음.** 사소한 관찰 사항 2건과, 테스트
환경 자체의 한계로 실측이 불확실했던 항목 1건을 하단에 기록했습니다.

## 0. 사전 준비

- `refresh_unity(mode=force, compile=request)` → **컴파일 에러/경고 없음.** 가이드 0번 항목에서
  우려했던 "명명 인자(named argument)+위치 인자(positional argument) 혼용 문법"
  (`InstrumentAttackDispatcher.cs`, `ViolinOrbitEffect.cs`의 `Initialize(...)` 호출부)은 실제 컴파일로
  검증한 결과 **문제없이 컴파일됨**을 확인했습니다. C# 7.2부터 지원하는 "non-trailing named
  arguments" 규칙(명명 인자가 자신의 실제 선언 위치와 정확히 일치하는 동안은 그 뒤에 위치 인자가
  이어져도 합법) 그대로이며, 코드 리뷰로 검토했던 모든 호출부가 이 규칙을 만족합니다.

→ **PASS**

### 테스트 방법론: 이번 라운드에서 확장된 부분

1. **`OnHoldTick(float deltaTime)` 계열(바이올린/프렌치호른/첼로/팀파니)**: 기존과 동일하게 deltaTime을
   파라미터로 직접 주입해 완전히 결정론적으로 재현했습니다.
2. **`Update()`가 `Time.deltaTime`을 내부에서 직접 읽는 신규 클래스들**(`LingeringZoneEffect`,
   `AreaImpactEffect`, `HomingShrapnelProjectile`, `FluteVortexEffect`): 3단계에서 드럼 오라에 썼던
   기법을 재사용/일반화했습니다 — "카운트다운/타이머 필드(예: `remainingDelay`, `tickTimer`,
   `elapsed`)를 리플렉션으로 임계값 이상으로 직접 주입한 뒤 `Update()`를 `deltaTime=0`인 채로 한 번
   호출"하면, 조건 분기(`if (remainingDelay <= 0f) Impact();` 등)는 **이미 주입된 필드 값만으로
   판단**되므로 `deltaTime`이 0이어도 원하는 시점의 동작을 정확히 재현할 수 있었습니다. 이 방식으로
   착탄/틱/만료 로직 전부를 실시간 대기 없이 검증했습니다.
3. **`HomingShrapnelProjectile`의 도달(명중) 판정**: `step.magnitude >= dist`로 판정하므로, 목표와의
   거리를 아주 가깝게(0.001) 만들어두면 그 이후 어떤 `deltaTime`(심지어 에디터의 프레임 몰림으로 인한
   비정상적으로 큰 값)이 주어져도 반드시 도달 조건을 만족합니다. 이 성질을 이용해 실시간을 아주 짧게
   허용하는 방식으로 명중/피해 로직 자체는 안정적으로 검증했지만, **동시에 걸리는 0.5초 기절 상태는
   같은 실시간 창에서 만료 여부까지 확인하지 못했습니다** (4번 섹션 "확인 불가 항목" 참고).
4. **`EnemyMonster`의 신규 상태이상 인프라(`ApplyStun`/`ApplyTemporarySlow`/`SetDamageAmpMultiplier`)**:
   이 API들은 필드를 동기적으로 즉시 갱신하므로(내부적으로 `Time.deltaTime`을 전혀 쓰지 않음),
   호출 직후 리플렉션으로 필드를 읽는 것만으로 우선순위/오버라이드 로직(더 강한 효과 우선, `Mathf.Max`로
   덮어쓰지 않는 규칙 등)을 100% 결정론적으로 검증했습니다. 다만 이 상태들이 실제로 매 프레임
   `Time.deltaTime`만큼 감소하며 "이동 정지/재개"로 이어지는 부분은 아래 1번 섹션에서 별도로 다룹니다.

## 1. 공용 상태이상 인프라 (`EnemyMonster.cs`) — PASS (일부 항목은 코드 리뷰로 대체)

- **`ApplyStun` 기본 동작**: `ApplyStun(1.0f)` 직후 `IsStunned=True`, `stunTimer=1.0` 확인. 이미 걸린
  기절보다 **짧은** 기절을 추가로 걸어도(`ApplyStun(0.3f)`) 타이머가 줄어들지 않고 유지됨(`Mathf.Max`
  동작), 더 **긴** 기절을 걸면(`ApplyStun(2.0f)`) 정확히 연장됨을 확인.
- **`SetDamageAmpMultiplier` + `TakeDamage` 전역 적용**: 1.15배 증폭 상태에서 10 데미지 → 12(반올림,
  아래 참고), 1.0배로 복귀 후 10 데미지 → 10. 프렌치호른뿐 아니라 `TakeDamage`를 호출하는 모든
  공격에 전역 적용됨을 코드/실측으로 확인.
- **`ApplyTemporarySlow` vs `SetSpeedMultiplier` 우선순위**: `SetSpeedMultiplier(0.6)`(예: 첼로 지속
  감속) 상태에서 `ApplyTemporarySlow(0.5, 0.5)`(더 강한 한시적 감속)를 걸면 `tempSlowMultiplier=0.5`로
  갱신. 이미 0.5가 걸린 상태에서 더 **약한** `ApplyTemporarySlow(0.8, 1.0)`을 걸면 배율은 갱신되지
  않고(0.5 유지) 지속시간만 `Mathf.Max`로 연장(0.5→1.0)됨을 확인. 이후 더 **강한**
  `ApplyTemporarySlow(0.3, 0.2)`를 걸면 배율이 0.3으로 갱신되고 지속시간은 여전히 `Mathf.Max` 규칙을
  따름을 확인 — "더 강한(낮은) 배율 우선" 요구사항과 정확히 일치.
- **기절이 이동을 완전히 정지시키고, 해제 후 기존 감속 상태로 복귀하는지 (실시간 이동 검증, 부분적
  확인)**: `SetSpeedMultiplier(0.5)` 상태에서 `ApplyStun`을 걸면 `effectiveSpeedMultiplier`가 0이 되어
  이동이 멈추는 것을 소스 코드(`EnemyMonster.cs:96-99`)로 확인했고, 필드 상태 조합(스턴 타이머>0,
  `speedMultiplier`는 그대로 보존)도 리플렉션으로 확인했습니다. 다만 **실제 여러 프레임에 걸친 이동
  거리를 실시간으로 재보는 시도는 에디터 프레임 몰림 문제로 신뢰할 수 없어 포기**했습니다 — 아래
  "확인 불가 항목" 참고.

→ **PASS** (우선순위/오버라이드 로직은 필드 상태 기준 100% 확정적으로 확인, 실제 프레임 단위 이동
정지/재개는 코드 리뷰로 대체)

`HomingShrapnelProjectile.cs:45`에 `target.ApplyStun(stunDuration)` 호출이 소스 코드상 명확히 존재하고
`ApplyStun` 메커니즘 자체는 1번 섹션에서 별도로 완전히 검증되었으므로, 배선 자체는 올바르다고
판단합니다. 다만 라이브 환경에서 "명중 즉시 기절"이 실제로 관찰 가능한 지속시간을 갖는지는 이번
방법론으로는 결론 내리지 못했습니다.

## 12. 가이드 4번 섹션(알려진 단순화)에 대한 재확인

- **Target DPS 미검증**: 이번 라운드도 각 레벨의 실제 DPS를 목표치와 대조하는 정량적 밸런스 측정은
  수행하지 않았습니다(가이드에도 이번 라운드 범위 밖으로 명시됨). 별도 밸런스 패스가 필요합니다.
- **감속/기절 수치 임의값**: 드럼 Lv3 둔화 50%, 마림바 Lv5 감속 30%·1초 등은 실측상 코드에 작성된
  값 그대로 정확히 동작함을 확인했을 뿐, 수치 자체의 적정성은 검증 범위 밖입니다.
- **첼로 Lv4 "잔류시간" 재해석**: 코드가 "릴리즈 후 1.3초 잔류"로 구현되어 있고 실측으로도 정확히
  그렇게 동작함을 확인했습니다. 해석의 타당성 자체는 설계자 확인이 필요한 사안으로 남아있습니다.
- **글록켄슈필 Lv5 "타겟 없으면 스킵"**: 코드 로직(`FindSecondaryShrapnelTarget`이 `null` 반환 시
  스킵)은 정확하지만, 이 로직은 씬 전체의 `EnemyMonster`를 거리 제한 없이 검색합니다. 즉 실제 스킵은
  "화면상 근처에 다른 적이 없을 때"가 아니라 "맵 전체에 다른 적이 정말 한 마리도 없을 때"만 발생하며,
  일반적인 실제 플레이(항상 어딘가에 다른 몬스터가 존재)에서는 스킵 조건이 사실상 거의 발동하지 않을
  가능성이 있습니다. 유도 파편 자체도 최대 사거리/수명 제한이 없어, 이론적으로는 매우 먼 적을 향해
  발사될 수 있습니다. 버그라기보다는 "스킵 조건이 설계 의도만큼 자주 발동하지 않을 수 있다"는
  설계 참고사항으로 기록합니다.
