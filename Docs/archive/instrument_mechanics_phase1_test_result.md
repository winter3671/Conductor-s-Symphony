# 10종 악기별 공격 메커니즘 - 1단계(피아노/벨/마림바/글록켄슈필) 검증 결과

`instrument_mechanics_phase1_test_guide.md`에 정리된 절차에 따라 **Unity MCP(Unity 6000.5.5f1,
`My project` 인스턴스)**로 실측 검증을 진행한 결과입니다.

**종합 결과: 4종(피아노/벨/마림바/글록켄슈필)의 타겟팅·핵심 메커니즘·레벨 스케일링 전부 PASS. 발견된
버그 없음.** 홀드 노트(0단계) 상태머신도 추가로 스모크 테스트해 정상 확인.

## 0. 사전 준비

- `refresh_unity(mode=force, compile=request)` → `ready_for_tools=true`, 컴파일 에러 없음. 콘솔에 남은 건
  MCP 플러그인 자체의 WebSocket 경고 1건뿐 (프로젝트 코드와 무관).
- Play Mode 진입 직후 `Application.runInBackground = true` 설정.

→ **PASS**

### 테스트 방법론: 실시간 대기(Bash sleep) 대신 결정론적 리플렉션 구동 방식 채택

처음에 가이드대로 "빔을 스폰하고 `Bash sleep`으로 실제 시간을 기다린 뒤 결과 확인"하는 방식으로 피아노를
테스트했더니, 관통된 적이 하나도 없고 테스트용 몹들이 전부 플레이어 위치 `(0,0,0)`으로 이미 수렴해있는
이상 현상이 나타났습니다. 원인은 이전 라운드(`balance_1to3_test_result.md`)에서도 관찰된 "에디터가
포커스를 잃으면 프레임을 불규칙하게(간헐적으로 몰아서) 처리하는" 환경 특성으로 추정됩니다 — 도구 호출
사이 실제 경과 시간이 예측 불가능하게 커지면서, 한 프레임에 거대한 `Time.deltaTime`이 몰려 빔이 적들을
그대로 스킵하고 지나가 버린 것으로 보입니다(적들도 같은 이유로 순간이동하듯 플레이어 쪽으로 수렴).

이후로는 **`Time.timeScale = 0f`로 자동 갱신을 완전히 차단**하고, 검증이 필요한 오브젝트의 `private
Update()`/`CheckHits()` 등을 리플렉션으로 직접 호출하거나 위치·경과시간 필드를 직접 세팅해서 원하는
지점을 결정론적으로 재현하는 방식으로 전환했습니다. 아래 모든 결과는 이 방식으로 얻은 것입니다.
(다음 라운드를 위한 팁: 발사체/타이머 기반 메커니즘을 Unity MCP로 검증할 때는 처음부터 이 방식을
쓰는 걸 권장합니다.)

## 1. 피아노 — PASS

`CombatTargetingUtility.GetNearestEnemy()` 기준 최근접 방향으로 관통 레이저 발사.

| 레벨 | 검증 항목 | 결과 |
|---|---|---|
| Lv1 | 방향=최근접 적 방향(다른 방향의 먼 적 아님), 관통=2, 발사수=1 | PASS |
| Lv3 | 관통=4 (4마리 일렬 배치 시 전부 명중) | PASS |
| Lv4 | 발사수=2 (동시 판정 1회에 빔 2개 스폰) | PASS |
| Lv5 + combo=6 | 기본 2발 + 부채꼴 3발 = 총 5발 | PASS |
| Lv5 + combo=5 (6의 배수 아님) | 부채꼴 미발동, 2발만 | PASS |

**관통 실측 방법**: 빔을 정확한 지점(거리 2/3/4 등)에 위치시키고 `CheckHits()`를 직접 호출해, 관통 카운트가
정확히 소진되는 지점까지만 적이 맞고 그 이후 적은 안 맞는지 확인.
```
waypoint=(2,0,0) 통과 후 remainingPierce=1
waypoint=(3,0,0) 통과 후 remainingPierce=0
eNear=99995, eMid=99995, eFar=100000(안맞음), eOther=100000(다른방향, 안맞음)
```

## 2. 벨 — PASS

`CombatTargetingUtility.GetNearestEnemy()`로 찾은 **적의 위치**를 중심으로 8방향 발사 (플레이어 위치가
아님을 확인).

| 레벨 | 사거리(range) | 관통(pierce) | 발사(bursts) | 빔 개수 |
|---|---|---|---|---|
| Lv1 | 2.5 | 3 | 1 | 8 |
| Lv2 | 3.25 | 3 | 1 | 8 |
| Lv3 | 4.0 | 5 | 1 | 8 |
| Lv4 | 4.75 | 5 | 2 | 16 |
| Lv5 | 5.5 | 5 | 2 | 16 |

전부 실측값과 정확히 일치 (`Mathf.Approximately` 기준 ALL OK). 8방향 각도도 -180/-135/-90/-45/0/45/90/135로
정확히 45도 간격 확인. 8개 빔의 시작 위치가 전부 "최근접 적 위치"와 일치하고 플레이어 위치와는 다름을
좌표 비교로 확인 (기획 의도인 "적 중심 8방향" 정확히 구현됨).

## 3. 마림바 — PASS

`PlayerController.GetFacingDirectionVector()` 방향으로 직선 파동 발사.

- **방향 추적**: `facingDirection`을 리플렉션으로 `Right`/`Up`으로 각각 바꿔가며 발사 → 빔 방향이 정확히
  `(1,0,0)` / `(0,1,0)`로 일치. "이동을 멈춰도 마지막으로 바라본 방향을 유지"하는 설계와 일치(별도 이동
  입력 없이 `facingDirection` 필드 값만으로 결정되므로 자연히 만족됨).
- **관통**: Lv1=3, Lv2=5 → 정확.
- **바운스 플래그**: Lv1~3 `bounceOnMaxRange=False`, Lv4 `=True` → 정확.
- **실제 바운스 동작** (결정론적 재현 — `traveledDistance`를 `maxRange`로 강제 세팅 후 `Update()` 직접 호출):
  ```
  초기 dir=(1,0,0)
  1차 최대사거리 도달 후 dir=(-1,0,0) (반전), hasBounced=True
  2차 최대사거리 도달 후 dir=(-1,0,0) 그대로 (재반전 없음 → Destroy 분기로 정상 전환)
  ```
  "최대사거리 도달 시 1회만 반전"이라는 기획 의도가 코드 그대로(`hasBounced` 가드) 정확히 동작함을 확인.

## 4. 글록켄슈필 — PASS

`CombatTargetingUtility.GetHighestHpEnemy()`로 찾은 **체력이 가장 높은 적** 위로 지연 낙하 광역.

- **타겟팅**: 가까운데 체력 낮은 적(hp50, 거리1)과 먼데 체력 높은 적(hp500, 거리10)을 동시에 배치 →
  낙하 지점이 정확히 체력 높은 쪽(거리10) 위치와 일치, 가까운 저체력 적은 무시됨. **"가장 가까운 적"이
  아니라 "체력 최고 적"임을 명확히 구분** — 가이드 체크리스트 항목 그대로 확인.
- **동률 타이브레이크**: HP가 같은 두 적(가까운 쪽/먼 쪽) 배치 시 더 가까운 쪽이 선택됨 → 기획 의도
  ("동률 시 근거리 우선")대로 정확.
- **스플래시 반경**: Lv1~2=0.6, Lv3+=1.1 → 정확.
- **Lv4 콤보 버스트**:
  | 콤보 | 낙하 개수 | 결과 |
  |---|---|---|
  | 2 (4의 배수 아님) | 1개 (버스트 없음) | PASS |
  | 4 (4의 배수) | 2개 (+1) | PASS |
  | 8 (8의 배수) | 3개 (+2) | PASS |
  | Lv3+combo4 (레벨 미달) | 1개 (버스트 안 됨) | PASS |
- **낙하 지연**: `AreaImpactEffect`가 스폰 직후에는 데미지를 주지 않고(대상 HP 불변), `remainingDelay`가
  0 이하가 되는 시점에만 `Impact()`가 실행되어 데미지가 들어감을 확인 (스폰 직후 HP 500 유지 →
  지연 강제 만료 후 495로 정확히 5데미지 적용).

## 5. (선택) 홀드 노트 상태머신 스모크 테스트 — PASS

실제 키보드 입력을 코드로 강제하기 어려운 New Input System 특성상, `RhythmNote`의 홀드 상태머신과
`RhythmManager`의 이벤트 배선을 리플렉션으로 직접 검증했습니다.

- `RhythmNote.BeginHold()` → `HoldProgress01=0`으로 초기화 확인.
- `TickHold(deltaTime)` 누적 호출 → 0.5초 시점 `progress=0.5, stillHolding=True`, 누적 1.1초(지속시간 1.0초
  초과) 시점 `stillHolding=False, progress=1.0(clamp)` — 정확.
- `RhythmManager.UpdateActiveHolds()`의 "키가 눌려있지 않으면 조기 이탈" 경로: 테스트 환경에서 실제로
  아무 키도 누르고 있지 않은 자연스러운 상태를 그대로 이용해 검증 → `OnHoldTickEvent`는 발생하지 않고
  (`tickFired=False`), `OnHoldReleasedEvent(lane, progress, completed=False)`가 정확히 발생하며
  `activeHoldByLane` 슬롯도 정상적으로 `null`로 초기화됨을 확인.
- "키를 계속 누르고 있는" / "끝까지 완료" 경로는 실제 키 입력 시뮬레이션 한계로 이번엔 직접 재현하지
  못했으나, 해당 분기 코드(`OnHoldTickEvent?.Invoke`, `OnHoldReleasedEvent?.Invoke(lane, 1.0f, true)`)는
  위에서 검증한 "조기 이탈" 분기와 완전히 대칭 구조이고 `RhythmNote` 상태머신 자체는 이미 정확함이
  확인되어, 코드 리뷰 기준으로는 문제 없음으로 판단됩니다. 실제 키 입력을 통한 최종 확인은 사람이
  플레이하며 재확인하는 걸 권장합니다.
- 같은 레인에 홀드가 진행 중일 때 새 onset을 무시하는 로직(`ProcessSequencerStep`의
  `if (isHold && activeHoldByLane[(int)lane] != null) continue;`)은 코드 리뷰로 확인 — 조건문이 정확히
  겹침을 차단하도록 작성되어 있음.

## 6. 가이드에 명시된 알려진 단순화 사항 — 코드로 재확인

- **전역 콤보 공유**: `RhythmAttackManager.HandleRhythmHit`이 `RhythmManager.Instance.CurrentCombo`를 그대로
  피아노/글록켄슈필에 전달함을 코드로 재확인. 가이드 설명과 일치 (버그 아님, 설계자 확인 필요 항목).
- **마림바 엇박 구분 없음**: `ExecuteMarimba`에 엇박 여부를 판단하는 코드가 전혀 없고 `level>=2`만으로
  관통 강화가 결정됨을 확인. 가이드 설명과 일치.
- **Lv5 전용 효과 스텁**: 벨/마림바/글록켄슈필 모두 Lv5에서 Lv4와 다른 추가 분기가 없음(레벨 조건이
  전부 `>=` 형태라 Lv5는 Lv4 조건을 그대로 상속)을 코드로 확인 — 가이드 설명대로 미구현 상태.
