> **프로젝트명:** Conductor's Symphony (Unity / C# / Rhythm Roguelite)

> 리플렉션으로 읽는 방식까지 동원)으로 전부 검증

## 📌 1. 작업 배경 (Context)

실플레이 중 세 가지 리포트가 들어왔다.

1. 드럼의 상시 "비트 오라" 공격 범위가 화면에 안 보여서 감으로 플레이해야 한다.
2. 정박 타격 시 나가는 "비트 뱅" 충격파 모션 크기가 레벨을 올려도 항상 똑같아 보인다.
3. "범위 공격 증가" 패시브 카드를 먹어도 체감상 아무 변화가 없다.

세 가지 모두 언뜻 서로 다른 버그처럼 보였지만, 코드를 따라가 보니 한 뿌리에서 갈라져 나온 문제였다.
그리고 이 뿌리를 확인하는 과정에서, 원래 리포트에는 없던 훨씬 큰 문제 — 카드 시스템의 8개 패시브
스탯 중 3개가 프로젝트 전체에서 완전히 죽어있다는 사실 — 을 스스로 찾아내게 됐다.

## 🏗️ 2. 근본 원인 추적: 비주얼 버그 하나가 "죽은 스탯"으로 이어지다

### 2-1. 비주얼이 안 맞은 진짜 이유 — 근사 배율과 픽셀 좌표계의 불일치

`ShockwaveVisualEffect`(비트 뱅 모션)는 `radius * 2f`라는 근사 배율로 스프라이트 크기를 계산하고
있었는데, 이 배율은 실제로 쓰던 `CreateRingWithCore`가 32px 캔버스에 inner=12/outer=15라는
픽셀 좌표로 링을 그리는 방식이라는 걸 감안하지 않은 값이었다. 계산해보면 실제 화면에 그려지는
반경은 의도한 값의 약 0.3배에 불과했다 — 레벨업으로 판정 반경이 조금 커져도 화면상 차이가 거의
안 보였던 것도 같은 이유였다. `DrumAuraController`의 오라 링도 생성 시점에 딱 한 번 고정 크기로
그려진 뒤 갱신되지 않는 별개의 문제를 함께 갖고 있었다.

```csharp
// 신설: ProceduralSpriteFactory.CreateUnitRing — scale=1일 때 링 바깥쪽 끝이
// 정확히 "월드 유닛 반지름 1"이 되도록 pixelsPerUnit을 halfSize로 맞춘다.
public static Sprite CreateUnitRing(float innerRadius01, float outerRadius01, Color ringColor)
{
    const int size = 256; // 두께 1.5%까지 얇아지는 드럼 오라 링도 뭉개지지 않도록
    float halfSize = size / 2f;
    Vector2 center = new Vector2(halfSize, halfSize);
    return BuildSprite(size, (x, y) =>
    {
        float d01 = Vector2.Distance(new Vector2(x, y), center) / halfSize;
        return (d01 <= outerRadius01 && d01 >= innerRadius01) ? ringColor : Color.clear;
    }, halfSize);
}
```
이후로는 `transform.localScale = Vector3.one * 실제판정반경`만 하면 항상 정확히 일치한다. 장식용
링(보스/엘리트 상자/보스 투사체/악기 아이템)은 정확한 반경 매칭이 필요 없어 기존 `CreateRingWithCore`를
그대로 남겨뒀다 — 신규 인프라가 기존 사용처를 갈아엎지 않고 병행하도록 설계한 것이다.

### 2-2. "카드를 먹어도 체감이 안 된다"의 진짜 원인 — 계산 함수는 있는데 부르는 곳이 없었다

세 번째 리포트를 확인하러 `PassiveStatManager.GetRangeMultiplier()`를 찾아갔는데, 함수 자체는
"모든 공격 범위 +10%/Lv" 계산 로직이 정확히 구현돼 있었다. 문제는 **이 값을 실제로 곱해 쓰는
코드가 10종 악기, 15개 이상의 공격 이펙트 파일 어디에도 없었다**는 것 — 카드를 먹으면 스탯
레벨은 정상적으로 오르고 함수는 정확한 값을 리턴하는데, 그 반환값을 소비하는 지점이 통째로
누락되어 있어서 플레이어 입장에선 카드가 완전히 무의미했다.

## 🛠️ 3. 해결: 단일 헬퍼 계층 + 10종 악기 21개 지점 연동

### 3-1. `CombatTargetingUtility`를 패시브 배율의 단일 진입점으로 확장

각 악기 파일이 `PassiveStatManager.Instance`의 null 체크를 반복하지 않도록, 이미 타겟팅 헬퍼로
쓰이던 `CombatTargetingUtility`에 배율 3종을 래핑해 추가했다.

```csharp
public static float GetRangeMultiplier()
    => Passive.PassiveStatManager.Instance != null
        ? Passive.PassiveStatManager.Instance.GetRangeMultiplier() : 1f;   // 크레센도, 사거리에 곱함

public static float GetCooldownMultiplier()
    // 반환값은 "감축률"이 아니라 "남은 비율"(0~1) — interval *= 이 값 형태로 그대로 곱하면 됨
    => Passive.PassiveStatManager.Instance != null
        ? 1f - Passive.PassiveStatManager.Instance.GetCooldownReductionFraction() : 1f; // 알레그로

public static float GetDurationMultiplier()
    => Passive.PassiveStatManager.Instance != null
        ? Passive.PassiveStatManager.Instance.GetDurationMultiplier() : 1f; // 페르마타, duration에 곱함
```

### 3-2. 10종 악기의 "사거리/반경"에 크레센도 연결

| 악기 | 반영한 파라미터 |
|---|---|
| 드럼 | 오라 반경, 비트 뱅 반경 |
| 피아노 | 빔 최대 사거리 |
| 벨 | 8방향 빔 사거리, **Lv5 잔향 반경** |
| 마림바 | 파동 최대 사거리 |
| 글록켄슈필 | 스플래시 반경 |
| 바이올린 | 궤도 칼날 반경, 참격 사거리, **Lv5 잔향 반경** |
| 프렌치호른 | 부채꼴 사거리 (각도는 별개 스탯이라 제외) |
| 첼로 | 중력장 반경 |
| 팀파니 | 캐논 반경, **Lv5 지진지대 반경**, 융단폭격 스플래시·오프셋 |
| 플루트 | 흡입 반경 |

팀파니의 "융단폭격"(홀드 중 랜덤 오프셋에 소형 착탄을 떨어뜨리는 기믹)은 판단이 필요했다. 고정
표적 하나를 기준으로 한 명중 확률은 `스플래시 원 넓이 ÷ 오프셋 정사각형 넓이` 비율(≈38.5%)로
결정되는데, 스플래시와 오프셋 중 하나만 배율을 곱하면 이미 튜닝된 이 확률이 크게 어긋난다
(스플래시만 늘리면 ~85%, 오프셋만 늘리면 ~17%로 계산됨). **둘에 정확히 같은 배율을 곱해야
확률이 배율과 무관하게 그대로 유지**된다는 걸 수학적으로 확정한 뒤 그렇게 결정했고, 이후 40회
반복 착탄 실측(미보유 25.0% vs 만렙 37.5%)으로 이론치(38.5%) 근방임을 확인했다.

### 3-3. 감사(Audit)로 드러난 나머지 두 사망 스탯 — 알레그로·페르마타

크레센도 연동을 마친 뒤, "혹시 다른 패시브도 이런 상태인가"를 확인하려고 8개 패시브 전부를
실제 소비 코드 유무 기준으로 grep 감사했다. 결과는 시포르찬도(데미지)·비바체(이속)·레조넌스
(픽업범위)·튜닝(피해감소)·크레센도(방금 고침) 5종은 정상 연결, **알레그로(쿨타임 감축)와
페르마타(지속시간 증가) 2종은 크레센도와 완전히 같은 패턴으로 죽어있었다** — `GetCooldownReductionFraction()`
/ `GetDurationMultiplier()` 계산 함수는 존재했지만 곱해 쓰는 코드가 어디에도 없었다.

같은 헬퍼 계층에 두 배율을 추가해 7개 파일(드럼·첼로·프렌치호른·팀파니·바이올린·벨·플루트)의
tick interval / duration에 연결했다. 무엇을 대상에 넣고 뺄지는 임의로 정하지 않고 세 가지
기준으로 판단했다 — 확정할 수 없는 지점은 사용자에게 직접 물어 결정했다.

- **주기적으로 반복 발동하는 값(interval)** → 알레그로 대상. 글록켄슈필/팀파니의 "착탄 지연"
  (0.05~0.15초)은 발동 주기가 아니라 화면 연출 지연이라 제외.
- **잔류 장판/필드의 유지시간(duration)** → 페르마타 대상. 단, 리듬 노트 자체의
  `HoldDurationSeconds`는 늘어나면 플레이어가 더 오래 버텨야 해서 오히려 불리해지므로 절대
  대상에서 제외 — "지속시간이 늘어나는 게 항상 좋은 게 아니다"라는 게임플레이 방향성을 코드
  레벨에서 지켰다.
- **세기(magnitude) 값** (`pullStrength`, `slowFraction` 등) → 셋 중 어느 패시브와도 무관해 제외.

## 🔬 4. 검증: 눈으로 안 보이는 "발동 주기"를 리플렉션으로 실측하다

크레센도(반경)는 스프라이트 크기나 히트박스 거리로 눈에 보이지만, 알레그로가 손대는 tick
interval은 화면에 드러나지 않는 내부 타이머 값이다. 게다가 드럼 오라·첼로 필드·프렌치호른
부채꼴 3곳은 interval을 별도 필드로 저장하지 않고 `Update()` 안에서 매번 인라인 계산하는
구조라 값을 직접 읽을 수도 없었다.

Unity MCP 세션에서는 이 문제를 두 방식으로 풀었다.

- **인라인 계산 3곳**: `tickTimer` 필드의 "리셋 경계"를 직접 탐지 — 임계값 근처에서 두 번
  나눠 호출해 리셋이 튀는지 확인하고, 드럼은 `EditorApplication.Step()`으로 실제 프레임을
  여러 번 돌리며 `tickTimer`가 몇 스텝마다 리셋되는지 카운트했다.
- **필드로 저장된 나머지**: `PassiveStatManager`의 private `acquired` 리스트를 리플렉션으로
  조작해 알레그로/페르마타 레벨을 0↔5로 오가며 `bombardInterval`, `lingerTimer`,
  `LingeringZoneEffect.duration`/`tickInterval` 등을 리플렉션으로 직접 읽었다.

| 검증 라운드 | 대상 | 결과 |
|---|---|---|
| 1차 | 드럼 오라/비트 뱅 반경 시각화, 레벨별 반경 증가 | PASS — 발견된 버그 없음 |
| 2차 | 나머지 9종 크레센도 연동(Lv0→Lv5, 정확히 1.5배) | PASS — 팀파니 명중률 25.0%/37.5%, 이론치 38.5% 근방 |
| 3차 | 홀드 노트 이동 추적 버그(아래 5절) | PASS |
| 4차 | 알레그로 8개 지점(정확히 0.70배), 페르마타 5개 지점(정확히 1.75배), 세 배율 동시 활성화 시 독립 동작 | PASS — 발견된 버그 없음 |

4차 검증에서는 알레그로+페르마타+크레센도 세 패시브를 동시에 만렙으로 켠 상태에서 팀파니 Lv5
지진지대 하나로 세 값을 한 번에 확인했다 — `radius`=1.500(크레센도만 반영), `tickInterval`=0.350
(알레그로만 반영), `duration`≈5.25(페르마타만 반영). 서로 다른 변수에 각각 곱해지며 간섭 없이
독립적으로 동작함을 확인했다.

## 🐞 5. 부산물: 실측 도중 발견한 별개의 버그 — 홀드 노트가 플레이어를 따라가지 않음

크레센도 검증 도중 "홀드 중 화살표 키로 이동하면 롱노트가 그 자리에 멈춰있다"는 리포트가 추가로
들어왔다. 원인은 `RhythmNote.Update()`가 홀드 중(`isHolding == true`)일 때 꼬리 비주얼만
갱신하고 위치(`UpdatePosition()`)는 `BeginHold()` 시점에 딱 한 번만 고정한 뒤 다시 손대지
않았기 때문 — 판정 링은 매 프레임 플레이어를 따라가는데 노트만 그 자리에 남아 눈에 띄게
어긋나 보였다. 홀드 중에도 매 프레임 `UpdatePosition(1f)`를 호출하는 한 줄로 고쳤고, 실제 공격
이펙트(칼날/부채꼴 등)는 원래도 플레이어 transform을 직접 참조해 무관했다는 것까지 교차 확인했다.

## 💎 6. 핵심 교훈 (Key Takeaways)

**"버튼을 눌러도 반응이 없다"는 리포트는 로직 버그가 아니라 "그 로직 자체가 아직 아무 데도
연결되지 않았다"는 신호일 수 있다.** 크레센도·알레그로·페르마타 셋 다 계산 함수는 정확했다 —
버그가 있었던 게 아니라 소비하는 코드가 애초에 존재하지 않았다. 이런 경우는 값을 디버깅해서는
못 찾고, "이 함수를 실제로 호출하는 곳이 있는가"를 grep으로 먼저 확인해야 드러난다.

**하나를 고치고 나면, 같은 클래스의 나머지도 같은 상태인지 감사하는 것 자체가 남는 작업이다.**
크레센도 하나만 고치고 끝냈다면 알레그로·페르마타는 계속 죽은 채로 남아있었을 것이다. "패시브
8개 전부를 실제 소비 코드 기준으로 훑어본다"는 한 단계를 추가한 것만으로 같은 패턴의 문제 2개를
더 찾아냈고, 그 발견은 처음 리포트에는 전혀 언급되지 않았던 범위 밖의 문제였다.

**보이는 값(반경)과 안 보이는 값(발동 주기)은 검증 난이도가 다르고, 그 차이를 인정하고 다른
도구를 써야 한다.** 반경은 히트박스 거리나 스프라이트 크기로 눈에 보이지만, tick interval은
인라인 계산이라 필드로도 안 남는 경우가 있었다. 이 경우 "타이머 리셋 경계 탐지"와 "private
필드 리플렉션 읽기"라는, 코드를 건드리지 않고도 내부 상태를 확인하는 방법을 상황에 맞게
따로 골라 써야 했다 — 하나의 검증 기법으로는 전체를 커버할 수 없었다.
