# 🏆 [Portfolio Case Study] "체력바가 안 움직여요" — 텍스트 HUD를 그래픽 바/아이콘으로 바꾸는 단순 작업에서 두 번째로 걸린 uGUI "값은 맞는데 화면엔 안 보이는" 렌더링 함정 추적기

> **작성자:** winter3671 (Role 3: 메인 게임플레이 & 오디오/리듬 엔진 프로그래머)
> **프로젝트명:** Conductor's Symphony (Unity / C# / Rhythm Roguelite)
> **핵심 성과:** `"HP: 80/100"` 텍스트를 그래픽 바/아이콘 HUD로 바꾸는 UI 작업 도중, `Image.Type.Filled`가
> `sprite == null`일 때 `fillAmount` 프로퍼티는 정상 갱신되지만 실제 화면엔 항상 100% 채워진 것처럼
> 보이는 uGUI 렌더링 함정을 발견 — 프로퍼티/리플렉션 조회만으로 "정상"이라 결론 냈다가 사용자의 실제
> 스크린샷 제보로 뒤집힌 뒤 근본 원인을 재추적해 수정, 총 6라운드의 실사용자 플레이테스트 피드백
> 루프로 검증 완료

---

## 📌 1. 작업 배경 (Context)

게임의 핵심 시스템(10종 악기 밸런스, 리듬 판정, 오디오 동기화)이 어느 정도 안정화된 뒤, 실제
플레이 화면을 다시 살펴보니 UI가 유니티 기본 폰트와 순수 텍스트로만 이루어져 있었다.

```
HP: 80 / 100
LV.3  EXP: 40 / 100
SLOTS: [Q: Piano Lv.2] [R: EMPTY] [W: LOCKED (Lv.10)] [E: LOCKED (Lv.15)]
```

전투 중 가장 자주 노출되는 정보인데도 완성도가 가장 떨어져 보인다는 판단으로 폰트 통일(갈무리
도트 폰트) 다음 우선순위로 이 작업을 잡았다. 목표는 명확했다 — 세 줄의 텍스트를 실제 채워지는
체력바/경험치바 그래픽과, 악기별 아이콘이 들어간 Q/W/E/R 슬롯 UI로 바꾸는 것. 언뜻 단순한
UI 스타일링 작업처럼 보였지만, 실제로는 uGUI의 렌더링 특성에 대한 이해가 없으면 프로퍼티
검증만으로는 절대 못 잡는 버그를 두 번이나 만들어내는 작업이었다.

## 🏗️ 2. 설계: 기존 인프라를 최대한 재사용하기

### 2-1. 씬 편집 없이 코드로 자동 생성 — `Ensure*Elements()` 패턴 재사용

이 프로젝트는 `[SerializeField]`로 씬/프리팹에 직렬화된 값이 C# 기본값을 덮어쓰는 문제를 여러 번
겪었던 이력이 있다. 그래서 보스 HP바·승리/패배 화면 등 이번 세션 이전에 추가된 UI들은 씬을 직접
편집하지 않고, `Awake()`에서 필드가 `null`이면 코드로 새로 만드는 `Ensure*Elements()` 패턴을
쓰고 있었다. HP/EXP 바와 악기 슬롯도 이 패턴을 그대로 따랐다 — `EnsureHealthExpBarElements()`,
`EnsureInstrumentSlotElements()` 두 메서드가 필요한 `Image`/`Text` 컴포넌트를 전부 런타임에
생성한다.

```csharp
// 씬/프리팹 편집 없이 안전하게 UI를 추가하는 확립된 패턴
private void EnsureHealthExpBarElements()
{
    if (hpBarFill != null && expBarFill != null) return; // 이미 있으면 재생성 안 함

    GameObject root = new GameObject("HealthExpBars");
    root.transform.SetParent(transform, false);
    // ... RectTransform 앵커/크기 설정 후 프레임 + 채움 Image 생성
}
```

### 2-2. 신규 아트 없이 기존 자산 재사용

악기 슬롯 아이콘은 이미 `Resources/Sprites/Instruments/{InstrumentType}.png` 10종이 존재했으므로
`Resources.Load<Sprite>($"Sprites/Instruments/{type}")`로 그대로 재사용해 신규 아트 제작 없이
해결했다. 반투명 프레임 배경도 실제 프레임 아트가 도착하기 전까지는 단색 사각형으로 대체하도록
설계해, 아트 파일이 나중에 `Resources/Sprites/UI/`에 채워지기만 하면 코드 수정 없이 자동으로
전환되게 만들었다 — 아트 파이프라인과 코드 파이프라인을 분리한 것이다.

### 2-3. 게임 로직 순서와 화면 표시 순서를 분리하기

악기 슬롯을 화면에 배치하면서 사소하지만 중요한 설계 판단이 하나 있었다. 실제 장착 데이터의
슬롯 인덱스는 `Q=0, R=1, W=2, E=3`(밸런스 기획 문서 원본 순서)인데, 리듬 판정 링은 화면에
`Q(180°/왼쪽) → W(135°/왼쪽위) → E(45°/오른쪽위) → R(0°/오른쪽)` 순서로 배치되어 있었다. 이
둘을 그대로 매핑해 슬롯 UI를 만들면 판정 링에서 보는 키 순서와 하단 슬롯 UI의 좌우 순서가
어긋나 플레이 중 혼동을 준다는 사용자 피드백이 들어왔다.

게임 로직(밸런스 데이터)과 화면 표시 순서는 서로 다른 관심사이므로, 데이터 구조 자체를 바꾸는
대신 **표시 전용 매핑 테이블 하나**로 분리했다.

```csharp
// 화면 좌→우 표시 순서(Q,W,E,R) → 실제 장착 슬롯 인덱스(Q=0,R=1,W=2,E=3)
private static readonly int[] SlotDisplayToDataIndex = { 0, 2, 3, 1 };

// UpdateInstrumentUI()에서:
for (int uiIndex = 0; uiIndex < 4; uiIndex++)
{
    int dataIndex = SlotDisplayToDataIndex[uiIndex]; // 그릴 때만 변환
    bool isLocked = dataIndex >= unlocked;           // 해금 판정은 여전히 실제 데이터 인덱스 기준
    // ...
}
```

게임 밸런스 로직(`GetUnlockedSlotsCount()`, 레벨 스탯 테이블 등)은 한 줄도 건드리지 않고, 그리는
쪽 코드에만 매핑 테이블을 끼워 넣어 문제를 해결했다 — 데이터와 표현을 분리하면 이런 "순서만
다르게 보여주고 싶다"는 요구가 안전한 국소 변경으로 끝난다.

## 🐞 3. 핵심 버그: "fillAmount는 정상인데 화면은 항상 꽉 차 보인다"

### 3-1. 1차 검증 — 프로퍼티 값만 보고 "정상"이라 결론 냄

체력/경험치 바는 `Image.Type.Filled` + `fillMethod = Horizontal`로 구현했는데, 채움 색은 단순한
단색이라 스프라이트를 따로 만들지 않고 `Image.color`만 지정했다.

```csharp
// 최초 구현 — sprite를 할당하지 않음
hpBarFill = hpFillObj.AddComponent<Image>();
hpBarFill.color = new Color(0.85f, 0.2f, 0.25f);
hpBarFill.type = Image.Type.Filled;
hpBarFill.fillMethod = Image.FillMethod.Horizontal;
hpBarFill.fillAmount = 1f;
```

1차 Unity MCP 검증에서는 `PlayerController.TakeDamage(60)`을 직접 호출한 뒤
`hpBarFill.fillAmount` 값을 씬 그래프에서 조회해 `0.4`로 정확히 바뀌었음을 확인하고 PASS 판정을
내렸다. 이후 사용자가 직접 플레이하며 "맞아도 체력이 줄어드는 게 안 보인다"고 제보했을 때도,
재검증 라운드에서는 몬스터 충돌을 자연스럽게 유도해 `fillAmount`가 `0.90 → 0.80 → 0.70 → 0.60`
순으로 정확히 바뀌는 로그까지 확인하고 다시 한번 "정상 동작"으로 결론지었다.

### 3-2. 진짜 원인 — 사용자의 실제 스크린샷이 뒤집은 결론

두 번의 "정상" 판정에도 불구하고 사용자는 세 번째로 스크린샷을 첨부해 다시 제보했다. "0 / 100"
텍스트가 떠 있는데도 빨간 바는 여전히 꽉 차 보이고, "100 / 250" 텍스트인데도 초록 바가 완전히
채워져 보인다는 것이었다 — **숫자 오버레이는 정확한데 시각적 채움 비율만 항상 100%로 고정**되어
있었다.

코드를 다시 열어 원인을 찾았다. uGUI의 `Image.Type.Filled`는 `sprite`가 `null`이면 `fillAmount`
프로퍼티 값 자체는 정상적으로 바뀌지만, **잘림(clip) 메시를 스프라이트의 UV 좌표 기준으로
생성하는 내부 로직이 동작하지 않아 화면엔 항상 꽉 찬 사각형으로만 렌더링**된다. 리플렉션/씬
조회는 `fillAmount`라는 숫자 하나만 보기 때문에 이 렌더링 단계의 문제를 절대 잡아낼 수 없었던
것이다.

이 프로젝트에는 사실 완전히 같은 부류의 함정을 겪은 전례가 있었다 — 배경 타일 스크롤 작업에서
`SpriteRenderer.material.mainTextureOffset`을 설정했는데, `Sprites-Default` 셰이더가
`_MainTex_ST`를 아예 읽지 않아서 프로퍼티 값은 정확히 바뀌는데 화면엔 전혀 반영되지 않았던
사례다. **"프로퍼티 값이 맞다"와 "화면에 실제로 그렇게 그려진다"는 별개**라는 교훈을 이미 문서에
남겨뒀는데도, 같은 프로젝트 안에서 다른 컴포넌트(`SpriteRenderer` → `Image`)로 형태를 바꿔 똑같은
함정에 다시 걸린 것이다.

### 3-3. 수정 — 이미 있던 유틸리티 재사용

해결 자체는 간단했다. 이펙트 시스템에서 이미 쓰고 있던 `ProceduralSpriteFactory`로 흰색 1x1
스프라이트를 만들어 채움 이미지에 할당하기만 하면 됐다.

```csharp
// 수정 후
hpBarFill.sprite = ProceduralSpriteFactory.CreateUnitSquare(Color.white);
hpBarFill.color = new Color(0.85f, 0.2f, 0.25f); // 색 지정 방식은 그대로 유지
hpBarFill.type = Image.Type.Filled;
```

`Image.color`로 틴트하는 방식은 그대로이므로 붉은색/초록색 표시엔 전혀 영향이 없고, 딱
"잘림 메시를 생성할 수 있는 스프라이트가 있는가"라는 조건 하나만 충족시켰다. 재검증은 이번엔
프로퍼티 조회가 아니라 `TakeDamage(45)`로 HP 50%대를 실제로 만든 뒤 **스크린샷으로 채움 비율을
육안으로 확인**하는 방식으로 진행했고, 절반만 채워진 바와 완전히 빈 바("YOU DIED" 상태) 둘 다
숫자와 정확히 일치하는 것을 확인했다.

## 🖼️ 4. 두 번째 함정: 나노바나나로 생성한 UI 프레임 아트의 해상도-표시크기 불일치

사용자가 나노바나나(이미지 생성 AI)로 만든 HP/EXP 바 테두리, 악기 슬롯 테두리 아트 3종을
`Resources/Sprites/UI/`에 배치한 뒤, 9-slice(`Image.Type.Sliced`)로 표시하기 위해 원본 PNG의
알파 채널을 Python으로 픽셀 분석해 `spriteBorder` 값을 추정해 넣었다. 그런데 실측해보니 EXP
바 프레임은 작은 조각으로 깨지고, 악기 슬롯 프레임은 아예 안 보이는 문제가 나타났다.

원인은 **원본 아트 해상도와 실제 표시 크기의 극단적인 불일치**였다 — 예를 들어 악기 슬롯 프레임은
`1254×1254` 해상도로 생성됐는데 실제 화면 표시 크기는 `124×124`였다. 추정한 테두리 두께
(`≈210px`, 원본 이미지 기준)가 실제 표시 크기보다 커버려서, Unity의 9-slice 모서리 연산 자체가
깨지는 것이었다.

정확한 테두리 픽셀 값을 다시 추정하는 대신, 더 근본적인 결정을 내렸다 — 이 아트들은 화려한 모서리
장식이 있는 게 아니라 얇은 단색 테두리 위주였으므로, `Image.Type.Sliced`를 버리고
`Image.Type.Simple`로 전환했다. Simple은 border 값을 아예 무시하고 스프라이트 전체를 타겟
RectTransform 크기에 맞춰 단순히 늘려 그리기 때문에, 해상도-대-표시크기 불일치라는 문제 자체가
원천적으로 사라진다. 정확한 픽셀 수치를 계속 추정하며 맞추는 대신, "이 디자인엔 9-slice가 애초에
필요하지 않다"는 판단으로 문제 클래스 자체를 없앤 것이다.

## ✅ 5. 검증: 6라운드에 걸친 실사용자 플레이테스트 피드백 루프

이 작업은 Unity MCP 자동 실측과 사용자의 실제 플레이 스크린샷 제보가 번갈아 이어지는 6라운드의
반복 검증을 거쳤다.

| 라운드 | 발견된 문제 | 조치 |
|---|---|---|
| 1차 | 레거시 텍스트 오브젝트가 삭제 안 돼 새 HUD와 중복 표시, 기존 Score/Combo 텍스트와 좌표 겹침, 잠금 레벨 라벨 인덱스 오표기 | 이름 기반 런타임 비활성화, 좌표 재배치, 매핑 배열 수정 |
| 2차(사용자 실플레이) | 체력바 미동작(1차 오판), 사망 시 음악 미정지, 악기 슬롯 크기 부족, 슬롯 순서 혼동 | 진단 로그 추가, 오디오 일시정지 로직 연결, 2.2배 확대, 표시 순서 매핑 분리 |
| 3차 | 숫자 병행 표시 방식 결정(바 중앙 오버레이 + 검은 Outline) | 흰 글씨+Outline 조합으로 어떤 배경 색 위에서도 대비 확보 |
| 4차(사용자 실플레이) | **체력바 미동작 재발 — 진짜 원인 발견** | `Image.Type.Filled` + `sprite=null` 렌더링 버그 수정 |
| 5차(사용자 실플레이) | 9-slice 프레임 깨짐(EXP 조각남, 슬롯 안 보임) | `Sliced` → `Simple` 전환 |
| 6차(사용자 직접 수정) | 채움 바가 테두리 밖으로 삐져나옴, 레벨 라벨 세로 정렬 | 사용자가 직접 여백 수치 확정, 라벨 높이를 바 높이와 통일 |

마지막 라운드는 `PlayerController.TakeDamage(45)`로 HP 45/100 상태를 실제로 재현한 스크린샷에서
채움 바가 프레임 안쪽에 정확히 들어맞는지, 숫자와 채움 비율이 일치하는지를 육안으로 재확인하는
것으로 마무리했다 — 3-1절의 교훈을 반영해, 이번엔 프로퍼티 조회가 아니라 처음부터 끝까지
스크린샷 기반으로 검증했다.

## 💎 6. 핵심 교훈 (Key Takeaways)

**"값이 맞다"와 "화면에 그렇게 보인다"는 별개의 명제이고, 같은 프로젝트 안에서도 반복해서 걸릴 수
있다.** 배경 스크롤의 `mainTextureOffset`과 이번 `Image.Type.Filled`는 컴포넌트도 다르고 증상도
달랐지만, 근본 구조는 동일했다 — 프로퍼티 setter는 성공했지만 렌더링 파이프라인의 특정 단계가
그 값을 실제로 소비하지 않는 경우였다. 리플렉션/씬 그래프 조회는 이런 종류의 버그를 원천적으로
잡아낼 수 없다. 값 검증과 별개로 **실제 렌더링 결과를 스크린샷으로 확인하는 단계를 항상 끼워
넣어야** 한다는 걸 두 번째로 절감했다.

**자동화된 검증(execute_code, 리플렉션)이 "PASS"를 반환해도, 실사용자의 반복적인 실플레이
피드백을 대체할 수 없다.** 이번 작업에서 체력바 버그는 자동 검증 라운드에서 두 번이나 "정상
동작"으로 결론 났다가, 세 번째로 사용자가 직접 스크린샷을 다시 보내준 뒤에야 뒤집혔다. 자동화된
검증은 "내가 확인하려고 정한 방식으로는 문제가 없다"만 보장할 뿐, 사용자가 실제로 겪는 문제를
보장하지 않는다.

**정확한 수치를 계속 추정하기보다, 문제 클래스 자체를 없애는 선택이 나을 때가 있다.** 9-slice
테두리 두께를 픽셀 단위로 계속 재추정하는 대신 `Type.Simple`로 전환한 결정이 그 예다. 디자인이
애초에 9-slice의 이점(모서리 보존)을 필요로 하지 않는다면, 정밀도를 높이려 애쓰기보다 그 정밀도가
왜 필요한지부터 재검토하는 게 더 빠른 길이었다.

**게임 로직의 데이터 순서와 화면 표시 순서는 분리해서 설계해야 한다.** 판정 링의 시각적 배치와
슬롯 UI의 좌우 순서가 어긋난다는 사소해 보이는 피드백을, 데이터 구조를 건드리지 않고 표시 전용
매핑 배열 하나로 해결했다 — 이렇게 분리해두면 "표시만 다르게 하고 싶다"는 요구가 항상 안전한
국소 변경으로 끝난다.
