# 🏆 [Portfolio Case Study] "효과는 다 구현했는데 숫자는 확인 안 했다" — 노트 타이밍 시뮬레이션으로 잡아낸 10~100배 DPS 밸런스 갭과 저위험 중앙집중형 보정

> **작성자:** winter3671 (Role 3: 메인 게임플레이 & 오디오/리듬 엔진 프로그래머)
> **프로젝트명:** Conductor's Symphony (Unity / C# / Rhythm Roguelite)
> **핵심 성과:** `game_balance_design.docx`가 요구하는 악기별 Target DPS(예: 30→45→70→100→150)와 실제
> 코드가 만들어내는 DPS 사이의 격차를, 32스텝 노트 패턴과 홀드 중첩 스킵 규칙까지 시뮬레이션한 이론
> 계산으로 먼저 정량화(대부분 목표의 1~20% 수준으로 확인)하고, 개별 악기 로직은 건드리지 않는
> 단일 진입점 보정 배율 테이블로 해결한 뒤, Unity MCP 실측 3라운드로 벨의 "8방향 전부 명중" 같은
> 구조적 진실을 찾아내 전 종목을 목표 범위(0.7~1.3배) 안으로 수렴시킴

## 📌 1. 작업 배경 (Context)

10종 악기 전부가 `10종 악기별 공격 메커니즘 기획서.docx`와 `game_balance_design.docx` 5번 항목이
요구하는 "효과의 종류·레벨별 적용 시점"을 코드로 전부 구현하고 Unity MCP 실측까지 통과한 뒤였다.
그런데 **"효과가 맞다"는 것과 "그 효과가 밸런스 doc이 명시한 Target DPS(피아노 등 Lv1~5:
30→45→70→100→150, 드럼: 60→75→130→180→300)에 도달하는가"는 완전히 다른 질문이었고, 이건 아직
한 번도 확인된 적이 없었다.** 밸런스 doc은 "10분 시점 4개 무기 기본 DPS 합 750"이라는 숫자를 근거로
보스전 클리어 타임(120초, HP 180,000)까지 설계해뒀기 때문에, 이 숫자가 실제로 맞는지는 게임이
플레이 가능한 밸런스인지를 좌우하는 문제였다.

## 🏗️ 2. 구현 내역 (What Was Built)

### 2-1. "손으로 계산하기 전에, 실제 타이밍 규칙부터 정확히 시뮬레이션"

DPS 어림값을 내려면 "악기가 초당 몇 번 타격하는가"부터 정확해야 했다. 32스텝 노트 패턴 문자열을
코드로 직접 파싱해 레벨별 노트 개수를 셌는데(코드 주석에 적힌 숫자는 신뢰하지 않고 문자열 자체를
셈 — 이 과정에서 벨 Lv4/5 주석이 실제와 다름을 별도로 발견), 홀드형 4종은 여기서 끝나지 않았다.
`RhythmManager.ProcessSequencerStep()`을 다시 읽어보니 **같은 레인에 이미 홀드가 진행 중이면 새
노트를 스폰하지 않는** 규칙이 있었다.

```python
# 32스텝 패턴 + 홀드 길이를 4루프(128스텝) 시뮬레이션해 정상상태 발동 횟수를 구함
active_until = -1
for g in range(total_steps):
    step = g % 32
    if pattern[step] == 1 and g >= active_until:
        triggers.append(g)
        active_until = g + hold_length_steps  # 이미 홀드 중이면 다음 onset은 통째로 스킵
```
결과는 예상 밖이었다: **바이올린·첼로·팀파니는 홀드 길이(13~16스텝)가 길어서, 레벨을 올려 노트
밀도를 아무리 촘촘히 짜도 실제 홀드 시작 횟수가 루프당 2회로 고정**됐다. 이 3종은 레벨업에 따른
DPS 증가를 전부 "홀드 1회당 데미지"로만 만들어야 한다는, 코드를 보는 것만으로는 알 수 없던 제약을
먼저 확정한 것이다.

### 2-2. 이론 추정으로 격차의 크기부터 빠르게 정량화

정확한 지오메트리(빔이 몇 발이나 동시에 맞는지 등)는 이론으로 확정할 수 없지만, "격차가 대략 몇
배인가"는 보수적 가정만으로도 충분히 가늠할 수 있었다. Python으로 10종 × 5레벨 전체의 단일 타겟
DPS를 계산해보니 **대부분 목표의 1~20% 수준(10~100배 부족)**이었다 — 원인은 공유 `baseDamage`
(레벨 무관 2~4)가 애초에 목표 스케일에 한참 못 미치는 값이었기 때문. 이 정도 배수 차이는 개별 악기의
관통/범위 같은 세부 수치 문제가 아니라 "타격 1회당 데미지" 자체의 스케일 문제라는 결론을 이론
계산만으로 먼저 확정했고, 이걸 근거로 방향(악기별 전용 데미지 테이블 신설 vs 공유 공식 자체를 상향)을
사용자와 확인받은 뒤에 진행했다.

### 2-3. 개별 악기 로직은 그대로 두는 단일 진입점 보정

```csharp
// Assets/Scripts/Instrument/InstrumentDamageTable.cs — 신규
public static float GetDamageMultiplier(InstrumentType type, int level) { ... }

// RhythmAttackManager.HandleRhythmHit() — 유일한 적용 지점
float instrumentDpsMultiplier = InstrumentDamageTable.GetDamageMultiplier(hitInstrument.type, hitInstrument.level);
int damage = Mathf.Max(1, Mathf.RoundToInt(baseDamage * mRhythm * mStat * instrumentDpsMultiplier));
```
10개 파일에 흩어진 악기별 관통/범위/발사수/틱 간격 로직은 전혀 건드리지 않고, 데미지가 계산되는
**단 한 지점**에만 악기·레벨별 배율을 곱했다. 배율 값은 "목표 DPS ÷ 이론 추정 DPS"로 역산했다.
드럼은 "비트 뱅"과 "비트 오라"가 서로 다른 코드 경로(`HandleRhythmHit` vs `UpdateDrumAura`)를 타기
때문에, 배율 계산 기준이 "둘의 합산치"였다는 걸 놓치면 오라 몫만큼 계속 목표에 미달하게 되므로
두 지점 모두에 같은 배율을 적용해야 했다 — 배율표 하나를 두 곳에 일관되게 연결하는 것도 검토
대상이었다.

## 🔬 3. Unity MCP 실측으로 드러난, 이론으로는 알 수 없던 진실

1차 배율 적용 후 실측(단일 고정 더미, 정확히 1루프=9.897초 동안 실제 코드 경로로 노트 패턴 재생)
결과 10종 중 6종은 바로 합격(0.7~1.3배)했지만, **4종에서 목표를 1.7~9배 초과하는 격차**가 새로
드러났다 — 이론 추정이 "덜 잡았던" 것과 정반대로, 이번엔 "과소평가"가 원인이었다.

### CASE. 벨 — 8방향 발사가 전부 같은 타겟에 명중하는 구조 (배율 문제가 아니었음)

이론 추정은 "8방향 중 1발만 명중한다"는 보수적 가정을 깔고 배율을 역산했다. 그런데 실제 코드는:

```csharp
// ExecuteBell() — 발사 원점이 플레이어가 아니라 "가장 가까운 적의 현재 위치"
Vector3 center = nearest.transform.position;
for (int i = 0; i < 8; i++) SpawnBeam(center, dir, ...); // 8개 빔이 그 적과 거리 0으로 겹쳐서 출발
```
실측 Lv1 8.08배, Lv5 9.15배 초과 — 가장 가까운 적은 8(Lv4+는 16)방향 빔 전부와 거리 0에서
겹쳐 있어 **항상 전부 명중**했다. 메커니즘 doc의 "가장 가까운 적 중심 8방향 성광" 서술 그대로였던
것이라 버그는 아니었지만, 배율을 역산할 때 이 사실을 놓쳤던 것이다.

### CASE. 팀파니 Lv5 — 쿨다운 없는 장판 생성이 기하급수적으로 누적

```
착탄 간격 ≈ 0.43초, 장판 수명 = 3초 → 한 착탄 주기 동안 최대 ~7개 장판이 동시에 잔존
```
Lv5는 모든 착탄마다 3초짜리 지진지대를 새로 생성하는데, 생성 간격(0.43초)이 수명(3초)보다 훨씬
짧아 여러 개가 겹쳐 쌓였다. 실측 2회 홀드에서 지진지대 피해만 목표 총딜량의 254%에 달했다(3.07배
초과). 바이올린 Lv5(잔향 9개 동시 생성, 1.82배 초과)와 글록켄슈필 Lv5(유도 파편 딜량이 이론 추정
계산에서 통째로 누락, 1.70배 초과)도 같은 패턴 — **레벨 5 전용 부가 효과의 실제 딜량 기여가 1차
이론 계산에서 일관되게 과소평가**돼 있었다.

## 🛠️ 4. 해결 방법 (The Fix)

실측 비율을 근거로 배율만 2차 재조정했다(코드 로직은 그대로 유지):

```csharp
// 벨: 실측 Lv1 8.08배 · Lv5 9.15배 초과 → 그 비율로 나눠서 "항상 전부 명중"을 기준으로 재계산
{ InstrumentType.Bell, new float[] { 9.3f, 7.0f, 5.8f, 3.0f, 2.9f } }, // 기존 75.0~26.3에서 대폭 하향
// 글록켄슈필 Lv5: 15.2 → 8.9 (유도 파편 딜량 반영)
// 바이올린 Lv5: 9.0 → 4.9 (잔향 9개분 반영)
// 팀파니 Lv5: 23.1 → 7.5 (지진지대 중첩분 반영)
```
바이올린/팀파니 Lv5는 배율만 낮춰서 수치는 목표에 맞췄지만, 잔향 개수·장판 생성 쿨다운 같은 구조
자체는 손대지 않았다 — "Lv5를 찍었을 때의 화면 임팩트가 옅어질 수 있다"는 점은 팀 리뷰 문서에 별도로
남기고, 수치 문제가 아닌 플레이 감각 문제로 분류해 코드는 최소 변경으로 마무리했다.

## ✅ 5. 검증 (3라운드 실측 경과)

| 라운드 | 대상 | 결과 |
|---|---|---|
| 1차 실측 (1차 배율) | 10종 × Lv1/Lv5 우선 측정 | 6종 PASS / **벨(전레벨)·글록켄슈필Lv5·바이올린Lv5·팀파니Lv5 FAIL(1.7~9배 초과)** / 팀파니Lv1 경계미달 |
| 2차 재조정 | 위 4개 항목 배율만 실측 비율로 재계산 | 코드 반영 완료, 재측정 대기 |
| 3차 실측 (2차 배율) | 벨 Lv1/Lv3/Lv5 + 나머지 Lv5 재측정 | **전부 PASS(0.86~1.05배)** — 벨은 중간 레벨(Lv3)도 추가 검증해 보간 전략 유효성까지 확인 |

3차 실측 과정에서 게임 버그는 아닌 테스트 방법론 이슈도 하나 발견됐다 — 글록켄슈필 Lv5의 2차 타겟
탐색이 전역 스캔이라, Play Mode에 남아있던 실제 스폰 몹을 측정용 보조 더미보다 가까운 타겟으로
잘못 선택한 사례였다. 씬을 완전히 격리(`DestroyImmediate`로 기존 적 전부 제거)한 뒤 재측정해 해결
— "전역 스캔 기반 타겟팅"을 가진 기능은 항상 씬을 완전히 격리한 상태에서 측정해야 한다는 것을
재확인했다.

## 💎 6. 핵심 교훈 (Key Takeaways)

**"효과가 doc과 일치한다"와 "그 효과의 크기가 doc의 목표 수치에 도달한다"는 서로 완전히 다른
검증이고, 둘 다 확인하기 전까진 어느 쪽도 끝난 게 아니다.** 4단계에 걸친 메커니즘 구현은 매 단계
실측을 통과했지만, 그 실측은 전부 "코드가 의도대로 동작하는가"만 봤을 뿐 "그 결과가 숫자로 목표에
맞는가"는 범위 밖이었다. 두 가지는 겹치지 않는 검증이라, 하나를 아무리 꼼꼼히 해도 다른 하나를
보증해주지 않는다.

**이론 계산은 "격차가 존재하는가"와 "대략 몇 배인가"를 빠르게 확정하는 데는 강력하지만, "왜 정확히
그 배수인가"는 실측 없이는 알 수 없다.** 노트 타이밍 시뮬레이션(홀드 중첩 스킵 규칙)은 코드를 그대로
따라간 결정론적 계산이라 100% 신뢰할 수 있었지만, 데미지 지오메트리(빔이 몇 발 겹쳐 맞는지, 장판이
몇 개나 동시에 쌓이는지)는 가정을 아무리 보수적으로 잡아도 실제 엔진 동작과 어긋날 수 있었다. 이
프로젝트에서는 그 어긋남이 8~9배(벨)까지 벌어졌다 — 이론과 실측 중 하나만 썼다면 각각 "격차의 존재를
못 봤거나(실측만)" "격차의 정확한 크기와 구조적 원인을 놓쳤을(이론만)" 것이다.

**시스템 전체의 스케일 문제는, 각 하위 시스템을 건드리지 않는 단일 진입점 보정으로 먼저 풀고,
그 다음에 구조적 문제를 개별적으로 솎아내는 순서가 낮은 리스크로 빠르게 수렴한다.** 10개 파일의
악기별 로직을 전부 다시 검증하는 대신, 데미지가 계산되는 딱 한 지점에 보정 배율을 꽂는 방식을
택했기 때문에 — 2차·3차 조정 모두 "배율 표 몇 줄"만 바꾸는 반복이었고, 그 와중에 드러난 진짜 구조적
문제(벨의 발사 원점, 팀파니의 쿨다운 없는 장판 생성)만 별도로 식별해 설계 검토 대상으로 분리할 수
있었다.
