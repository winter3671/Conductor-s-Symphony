# 🏆 [Portfolio Case Study] 10종 악기별 전용 공격 메커니즘 4단계 구현 & 두 기획서(메커니즘/밸런스) 교차 검증으로 잡아낸 "구현됐다고 착각한" 버그

> **작성자:** winter3671 (Role 3: 메인 게임플레이 & 오디오/리듬 엔진 프로그래머)
> **프로젝트명:** Conductor's Symphony (Unity / C# / Rhythm Roguelite)
> **핵심 성과:** `10종 악기별 공격 메커니즘 기획서.docx`를 4단계(탭 4종 → 홀드 4종 → 드럼/플루트 → `game_balance_design.docx` 5번 항목 레벨 성장표 정합화)에 걸쳐 전부 구현. 홀드 시스템 최초 실측에서 딕셔너리 순회 중 변경 크래시를 발견·수정했고, 두 기획서를 뒤늦게 교차 검토하는 과정에서 "구현되어 있으나 단순화됨"이라고 스스로 잘못 기록해뒀던 항목이 실은 **레벨 분기 자체가 통째로 빠진 버그**였음을 재확인해 바로잡음

---

## 📌 1. 작업 배경 (Context)

프로젝트 초기엔 10종 악기 전부가 "가장 가까운 적에게 원형 투사체 하나"라는 동일한 범용 로직
(`RhythmAttackManager`의 폴백 투사체)을 공유하고 있었다. `10종 악기별 공격 메커니즘 기획서.docx`는
악기마다 완전히 다른 공격 방식을 요구했다 — 피아노는 관통 레이저, 바이올린은 홀드 중 회전 칼날 +
릴리즈 참격, 드럼은 판정과 무관한 상시 오라 + 정박 타격 시 넉백 등. 노트 입력 방식도 둘로 갈렸다:
**탭(즉시 판정) 5종**과 **홀드(누르고 있는 동안 지속) 5종**. 0단계 리듬 판정 시스템은 탭 노트만
지원했기 때문에, 홀드 노트 판정 인프라(`RhythmManager.OnHoldTickEvent`/`OnHoldReleasedEvent`)부터
새로 깔아야 했다.

작업은 4단계로 나눠 진행했다: **1단계** 탭 4종(피아노/벨/마림바/글록켄슈필) → **2단계** 홀드 4종
(바이올린/프렌치호른/첼로/팀파니) → **3단계** 드럼(상시 오라라는 완전히 다른 성격의 지속 효과) +
플루트(숏홀드) → **4단계** 뒤늦게 발견한 `game_balance_design.docx` 5번 항목(악기별 Lv1~5 성장표)과의
불일치를 정합화. 각 단계는 Unity MCP 실측 검증을 거친 뒤에만 다음 단계로 넘어갔다.

## 🏗️ 2. 구현 내역 (What Was Built)

### 2-1. 홀드 5종을 위한 공용 생명주기 인터페이스

4종의 완전히 다른 홀드 메커니즘(회전 칼날, 부채꼴 지속 충격파, 고정 중력장, 즉발+융단폭격)을 하나의
파이프라인으로 다루기 위해 공용 인터페이스를 먼저 설계했다.

```csharp
// Assets/Scripts/Combat/InstrumentAttacks/IHoldAttackEffect.cs
public interface IHoldAttackEffect
{
    void Init(int level, int damage, Vector3 origin, Color color);
    void OnHoldTick(float deltaTime);
    void OnHoldReleased(bool completedFully);
}
```

`HoldEffectCoordinator`가 레인(`RhythmLane`)별로 `Dictionary<RhythmLane, IHoldAttackEffect>`를 관리하며
`BeginHold`/`Tick`/`Release` 세 진입점만 노출한다. `RhythmAttackManager`는 `IsHoldImplemented(type)`
분기 하나만 추가하면 됐고, 실제 각 악기의 로직(칼날 회전 각도 계산, 부채꼴 판정, 중력장 감속 등)은
전부 개별 `IHoldAttackEffect` 구현체 안에 격리됐다 — 인터페이스 하나가 "판정 성공 시 시작, 매 프레임
유지, 릴리즈 시 종료"라는 뼈대를 통일시켜준 덕분에, 4종을 순차로 추가하면서도 코디네이터/매니저 쪽
코드는 거의 변경이 없었다.

### 2-2. 드럼의 "판정과 무관한 상시 효과" — 파이프라인 밖에서 별도 처리

드럼은 나머지 9종과 근본적으로 다르다. 정박 타격 시 발동하는 "비트 뱅"은 기존 탭 파이프라인을
그대로 타지만, **판정 성공 여부와 무관하게 항상 켜져 있는 "비트 오라"**는 완전히 별개의 로직이
필요했다.

```csharp
// RhythmAttackManager.cs — 판정 이벤트와 별개로 매 프레임 독립 실행
private void Update() { UpdateDrumAura(); }

private void UpdateDrumAura()
{
    bool shouldBeActive = IsDrumsActive(); // "드럼이 언락된 슬롯에 장착되어 있는가"만 확인
    ...
    if (!drumAuraActive) return;
    drumAuraTickTimer += Time.deltaTime;
    if (drumAuraTickTimer < DrumAuraTickInterval) return;
    // 0.5초 간격으로 근접 적에게 소량 지속 타격 — M_rhythm은 의도적으로 제외(판정과 무관하므로)
}
```

이 구조 덕분에 "판정 트리거형 폭발딜"과 "판정 무관 baseline 딜"이라는 두 종류의 밸런스 축을 명확히
분리해서 다룰 수 있었다.

### 2-3. 공용 투사체/광역 클래스로 재사용성 확보

`PiercingBeamProjectile`(직선 관통)과 `AreaImpactEffect`(지연 낙하 광역)를 만들어, 피아노/벨/마림바/
바이올린 참격이 전자를, 글록켄슈필/팀파니가 후자를 공유하게 했다. 이후 4단계에서 상태이상(기절/피해
증폭/한시적 감속)과 잔류 장판(`LingeringZoneEffect`), 유도 파편(`HomingShrapnelProjectile`)을 추가할
때도 이 두 클래스에 `onHitEnemy`/`onImpact` 콜백만 얹어서 확장했다 — 악기 6종(마림바 Lv5 감속+밀쳐냄,
팀파니 Lv4 기절, 팀파니 Lv5 지진지대 등)이 전부 공용 클래스 몸체 하나를 재사용했다.

## 🔬 3. 실측/문서 교차검증으로 발견한 문제 2건

### CASE 1. 홀드 지속 타격 중 딕셔너리 순회 중 변경 크래시 (2단계 1차 실측에서 발견)

바이올린 회전 칼날의 히트 쿨다운 관리 코드가 `foreach`로 순회하는 도중 같은 딕셔너리를 인덱서로
갱신했다.

```csharp
// 수정 전 — 적을 한 번이라도 맞히면 다음 틱부터 100% 재현되는 크래시
foreach (var kv in hitCooldowns)
{
    float remaining = kv.Value - deltaTime;
    if (remaining <= 0f) hitCooldowns.Remove(kv.Key);
    else hitCooldowns[kv.Key] = remaining; // ★ 순회 중인 컬렉션을 인덱서로 수정
}
```
.NET은 이걸 `InvalidOperationException`으로 즉시 막는다. Unity MCP로 근접 적 1마리를 두고 홀드를
반복 틱하는 실측을 돌리자 두 번째 히트 직후 바로 재현됐다.

**수정**: 키를 먼저 `List<EnemyMonster>`로 스냅샷 뜬 뒤 그 리스트로 순회하며 원본 딕셔너리를
안전하게 수정하도록 변경. 2차 실측에서 다중 적 스트레스 테스트까지 포함해 재발이 없음을 확인했다.

### CASE 2. "구현되어 있으나 단순화됨"이라고 스스로 잘못 적어뒀던 완전한 공백 레벨 (4단계 문서 교차검토에서 발견)

1~3단계는 `10종 악기별 공격 메커니즘 기획서.docx`만 참고해서 진행됐고, `game_balance_design.docx`
5번 항목(악기별 Lv1~5 성장표)은 전혀 대조되지 않았다는 사실을 뒤늦게 발견했다. 두 문서를 교차
검토하며 구현 정리 문서 초안을 쓰는 과정에서, 마림바 Lv3("엇박 성공 시 파동 크기 +30%")를 처음엔
"오프비트 구분 없이 항상 적용됨(단순화)"이라고 서술했다. 그런데 실제 `ExecuteMarimba()` 코드를 다시
열어보니:

```csharp
// 수정 전 — 관통(Lv2)과 바운스(Lv4) 사이에 Lv3 조건 분기가 통째로 없음
int pierce = 3 + (level >= 2 ? 2 : 0);
bool bounce = level >= 4;
// sizeMultiplier 관련 코드 자체가 존재하지 않았음
```
Lv3에 해당하는 코드가 아예 없어서, "크기 증가가 항상 적용된다"는 것도 사실이 아니었다 — **레벨을
3으로 올려도 Lv2와 완전히 동일하게 동작하는 순수한 공백 레벨**이었다. 이건 "단순화"가 아니라
구현 누락(버그)이었고, 처음엔 그걸 "단순화"로 잘못 기록해뒀다는 것 자체가 문제였다.

**수정**: `sizeMultiplier = (level >= 3) ? 1.3f : 1f`를 추가하고, 문서의 잘못된 서술도 함께 정정.
4단계 Unity MCP 실측에서 Lv2/Lv3의 히트 반경 차이를 직접 비교해 정상 적용을 재확인했다.

## 🛠️ 4. 해결 방법 요약 (The Fix)

- **CASE 1**: 컬렉션 키 스냅샷 → 안전한 순회 중 수정 패턴으로 교체.
- **CASE 2**: 밸런스 doc 5번 항목을 악기 10종 전체에 대해 코드와 한 줄씩 대조하는 교차검토 표를
  만들어(`instrument_mechanics_implementation_summary.md` §4), 마림바 Lv3 외에도 레벨 임계값이
  한 단계씩 밀려 있던 항목들(프렌치호른 각도 확장 Lv4→Lv5, 팀파니 범위/빈도 Lv3→Lv2·Lv4→Lv3 등)을
  전부 doc 기준으로 정정했다. "코드가 의도대로 동작하는가"만 보는 실측 테스트로는 이런 종류의
  괴리(두 기획서 중 하나를 놓친 것)를 절대 잡을 수 없었다 — 문서 대 문서, 문서 대 코드를 줄 단위로
  대조하는 별도의 검토 단계가 필요했다.

## ✅ 5. 검증 (4단계 진행 경과)

| 단계 | 범위 | 1차 실측 | 재검증 |
|---|---|---|---|
| 1단계 | 탭 4종(피아노/벨/마림바/글록켄슈필) | PASS (버그 없음) | - |
| 2단계 | 홀드 4종(바이올린/프렌치호른/첼로/팀파니) | **FAIL** (바이올린 딕셔너리 크래시) | PASS (다중 적 스트레스 테스트 포함) |
| 3단계 | 드럼(상시 오라+비트 뱅) + 플루트(숏홀드) | PASS (버그 없음) | - |
| 4단계 | 밸런스 doc 5번 항목 전체 반영(레벨 임계값 정정 + 마림바 Lv3 버그 수정 + Lv4~5 부가효과 10종 신규 구현) | PASS (10종 전체 + 상태이상 공용 인프라) | - |

4단계에서는 기존에 없던 완전히 새로운 부가 효과(기절, 한시적 감속, 피해 증폭 디버프, 잔류 장판,
유도 파편, 지속 끌어당김)를 10종에 걸쳐 새로 추가하면서, 명명 인자(named argument)와 위치 인자가
섞인 `Initialize()` 호출부가 여러 곳(C# 7.2의 "non-trailing named arguments" 규칙 경계)에 생겨
컴파일 여부가 불확실했는데, 실측에서 전부 정상 컴파일됨을 확인했다.

## 💎 6. 핵심 교훈 (Key Takeaways)

**인터페이스로 "생명주기"를 통일하면, 서로 완전히 다른 메커니즘도 같은 파이프라인에 태울 수 있다.**
`IHoldAttackEffect`는 회전 칼날이든 부채꼴 충격파든 고정 중력장이든 신경 쓰지 않는다 — "시작/유지/
종료"라는 뼈대만 강제할 뿐, 실제 무엇을 하는지는 구현체에 위임한다. 덕분에 4종의 완전히 다른 홀드
메커니즘을 추가하면서도 `RhythmAttackManager`와 `HoldEffectCoordinator`는 거의 손대지 않았다 —
새 악기를 추가하는 비용이 "새 클래스 하나 + 스위치문 한 줄"로 수렴했다.

**여러 기획서를 순차로 참고하며 구현할 때는, 작업이 끝난 뒤 반드시 문서 간 교차검토 단계를 별도로
넣어야 한다.** 1~3단계는 메커니즘 doc만 보고 진행했고, 그 결과물은 각 단계의 실측 테스트를 전부
통과했다 — 즉 "코드가 그 순간 참고한 문서와는 정확히 일치"했다. 하지만 그 문서가 전체 기획의
절반이었다는 사실은 실측으로는 절대 드러나지 않고, 오직 "다른 문서를 나중에 펼쳐서 한 줄씩
대조"하는 별도의 검토 행위에서만 드러났다. 더 나쁜 건, 그 교차검토를 처음 할 때조차 마림바 Lv3
버그를 "단순화"로 오판할 뻔했다는 점이다 — **테스트가 통과했다는 사실도, 문서를 봤다는 사실도, 실제
코드를 다시 열어서 확인하는 것을 대체하지 못한다.** 어떤 판단이든 최종적으로는 소스 코드 자체가
근거여야 한다는 원칙을, 스스로도 한 번 어길 뻔하고서야 재확인했다.
